# Details

How BoosterAI works, per platform and per feature. For the overview see the [README](../README.md).

## How it works per platform

| | Terminal | Where tabs run |
|---|---|---|
| Windows | Windows Terminal (`wt.exe`), one tab per project with colour and title | The WSL distribution you choose (default `Ubuntu`), in your Windows folder (`C:\…` opens as `/mnt/c/…`) |
| Linux | `ptyxis`, `gnome-terminal`, `konsole`, `xfce4-terminal`, `kitty`, `wezterm` or `xterm` (chosen or auto-detected) | Locally |

Settings are stored in `%APPDATA%\BoosterAI\config.json` on Windows and `~/.config/BoosterAI/config.json` on Linux. A project entry is just a name and a directory, for example `C:\Projects\webshop` or `~/webshop`.

`BoosterAI --dry-run` prints the commands that Start would run, without opening anything.
The app follows the system's light or dark theme; `--theme light` or `--theme dark` overrides it.

## Settings

The settings window holds your projects (name and directory, with a folder picker), the tab colour theme, and where tabs run. On Windows you point at your normal Windows folders; WSL shares (`\\wsl.localhost\...`) and Linux paths such as `~/webshop` work too. Whether an agent then works in a mirror elsewhere is up to your own agent instructions.

### Find projects

**Find projects** (in the empty start window and at the bottom of Settings) searches your Documents folder (on Linux `~/Documents`, or your home folder when there is none) three levels down. A folder counts as a project when it has `.git` (a folder, or a file in worktrees) or one of `AGENTS.md`, `CLAUDE.md`, `AI.md`, `GEMINI.md`, `.claude/`, `.orchestra/`, `.agents/`, `.cursorrules` or `.github/copilot-instructions.md` in its root. The search does not go into a project it found, hidden folders, links, or folders such as `node_modules`, `bin` and `obj`. Projects you already have are left out; tick the ones to add and each becomes a tab named after its folder. *Search another folder* picks a different starting point, for example a WSL share such as `\\wsl.localhost\Ubuntu\home\me`.

### Font size

*Font size* in the settings window zooms the CLI text in all tabs (80–200 %; saved as `"ZoomPercent"` in `config.json`, `0` = the terminal's default font size). It applies on the next Start.

On Windows, BoosterAI writes `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\BoosterAI\boosterai.json` (a hidden "BoosterAI" profile with [`closeOnExit: "always"`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-advanced#profile-termination-behavior), plus `font.size` as a percentage of Windows Terminal's 12 pt default when an explicit zoom is selected; it inherits your other defaults) and opens the tabs with `-p BoosterAI`; at the default size the profile remains but omits `font`, inheriting your font settings. Only BoosterAI tabs select this profile, so your other profiles are unchanged. Windows Terminal reads fragments only when it loads its settings, so when the fragment changes while Windows Terminal is running, BoosterAI adds or removes one trailing newline in Windows Terminal's `settings.json` to make it reload, and waits two seconds before opening the tabs. That newline is the only change to your `settings.json`; your settings themselves are never touched.

On Linux all tabs open as tabs of ONE window in `gnome-terminal` and `xfce4-terminal` (a single call with `--window` and `--tab` groups), and in `ptyxis` (Ubuntu 25.10+ and Fedora default; `--tab-with-profile=default --new-window` to preserve multi-tab mode and visible tab bar, then `--tab` in that window, each call waiting for the previous one; when Ptyxis is not running yet, BoosterAI turns its `restore-session` setting off until the tabs are open, because a restored session reopens the last run's tabs as plain shells in their old windows and those take the tabs; this suppression requires `gsettings`). `konsole` uses `--separate --new-tab` and a separate window per tab to avoid targeting an unrelated existing window. `kitty`, `wezterm`, `xterm` and `x-terminal-emulator` have no tabs here, so each tab gets its own window. With `auto`, Ptyxis is tried first, then gnome-terminal and the rest in the order listed.

On Linux the zoom is passed to gnome-terminal (`--zoom`), kitty (`-o font_size`, 11 pt base) and wezterm (`--config font_size`, 12 pt base); other terminals (ptyxis, konsole, xfce4-terminal, xterm, ...) have no command-line option for it and ignore the setting. `BoosterAI --dry-run` prints the resulting commands and fragment.

## Appearance

*Appearance* in the settings window sets the app's light or dark look: **Auto** (follows the system, the default), **Light** or **Dark**. It is saved as `"AppTheme": "auto" | "light" | "dark"` in `config.json` and applies at once to all open windows. The command-line flag `--theme light|dark` wins over the config (used for screenshots). It does not affect the tab colour themes.

## Language

BoosterAI speaks Swedish and English. By default it follows the operating system's UI language (Swedish if that is Swedish, otherwise English). Choose **Automatiskt / Svenska / English** under *Language* in the settings window; the choice is saved in `config.json` (`"Language": "auto" | "sv" | "en"`) and **takes effect after BoosterAI is restarted**. The prompt sent to the AI when it installs the orchestra follows the chosen language too.

## The orchestra toggle

[Dirigenten och orkestern](https://github.com/solwation/dirigenten-och-orkestern) lets AI agents work through a project's GitHub issues. A conductor picks issues by priority, hands them to parallel worker agents in their own checkouts, then reviews and delivers the results.

The toggle appears only for projects that have it installed. Other projects show an "Install" link: a dialog explains what will happen, then the AI you chose opens in a new tab and installs it, asking you about the rules before it commits anything.

## Run once (non-interactive)

With the orchestra on, a **Run once** toggle per project (`"NonInteractive": true` in `config.json`) starts the CLI non-interactively with the orchestra command instead of an interactive session: `claude -p '/orkester'`, `agy -p '/orkester'` and `codex exec <orkester skill or /orkester>`. The tab shows live progress while it runs: for `claude` and `agy` the event stream (`--output-format stream-json`) goes through a small formatter in `tab-lib.sh` (`bs_stream`, uses python3 if present, otherwise a plain grep/sed fallback) that prints the assistant text, tool calls (`> Bash ls -la`), a `== turn done: N turns, X s` line after every finished turn (the CLI can keep running after a turn, e.g. waiting for background tasks) and, when the process really exits, a final `== exit <code>, total <s> s` line, and the CLI's own exit code is kept; `codex exec` already prints its progress. Without status tracking the tab falls back to the plain `-p` text mode. The tab keeps a normal shell afterwards so the output stays on screen. After each finished turn the formatter also logs `turn-done` in the tab log, and `turn-start` when the CLI writes again; while the CLI process lives on between the two (for example `claude -p` waiting for a background task), the tab shows *Watching · N min* (blue dot) with the minutes since the last turn ended, and the tooltip gives the time it ended. It goes back to *Running* when the CLI writes again. A successful exit shows *Idle* and its restart button starts another single pass; a failed run shows its exit code.

It means: one non-interactive session that ends by itself. You cannot answer or steer during the run, and tools that need approval are refused (no `--dangerously-*` flag is ever added). The toggle is disabled while the orchestra is off, and the install prompt always runs interactively.

Your alias for the CLI applies in Run once too (for example `alias agy='agy --dangerously-skip-permissions'`), so with such an alias nothing is denied. Without one, agy refuses every shell command without an allow-rule in `~/.gemini/antigravity-cli/settings.json` (`permissions.allow`, e.g. `command(git)`), ends the turn and still reports success. BoosterAI notices it: the formatter logs the denied command line, the tab shows *Denied: git, gh* (red, with a notification), and a bar in the main window offers **Allow and run again**. That adds `command(<program>)` for each program of the denied command line that is not allowed yet (on Windows in the WSL home), keeps everything else in the file and runs the affected tabs again. **Not now** hides the offer for those programs until BoosterAI restarts. `--mode auto` is no alternative: it needs agy's terminal sandbox. A rule allows the whole program, so `command(gh)` or `command(npm)` lets agy run anything those can do; review the list in `settings.json`. Detection needs python3 in the tab's Linux; `claude -p` denials are not detected yet.

It does not save tokens by itself: every turn sends the same context in both modes. In a test on #20 (claude haiku, a 34-line project) two identical one-shot runs differed more from each other than any mode difference could explain. How long each CLI waits for a background task after its turn ends was measured in #42 with a 62-minute background wait: `claude -p` stays alive and is re-invoked when the task finishes (62 minutes in the test); `codex exec` exits with status 0 as soon as the model ends its turn, because it has no tracked background tasks; `agy -p` waits at most 30 minutes (`waiting up to 30m0s for N background task(s)`), then ends the task and exits with status 0. BoosterAI never starts the CLI again by itself, whatever it could wait for.

**Idle watch with codex and agy.** An orchestra queue session that drains its queue keeps an idle watch (60 minutes in BoosterAI's own policy) and polls for new issues. `claude -p` keeps a background poll loop alive and wakes up when it finishes, so claude gets the plain command. For `codex exec` and `agy -p` such a loop would be dropped when the turn ends, so BoosterAI appends a host note to their orchestra command (`Launcher.ForegroundWatchNote`): `codex exec "$orkester (BoosterAI Run once host note: …)"` and `agy -p '/orkester (BoosterAI Run once host note: …)'`. It tells the session that the CLI exits with its turn and asks it to run every queue poll and the whole idle watch in the foreground of the turn, as blocking waits of at most 60 seconds (the core's interruptible waits), and to end the turn only when the session is finished. The CLI process then stays alive for the whole watch, the tab shows *Running* while it waits, and no second session is started. The cost is one short model call per wait (about 60 an hour with a cached context) instead of a sleeping background job. The note never goes into interactive tabs, the install prompt or claude. It is an instruction, not a guarantee: a model that ignores it still ends early, and the tab then shows *Idle* as before.

Verified in #49 with a stub queue project (an `orkester` skill over a local queue file, 60-second polls, a 3-minute idle watch) through the exact tab chain from `--dry-run` under `script`. `codex exec` (codex-cli 0.164.0) resolved the first item, polled every 60 seconds in the foreground, resolved an item added 75 seconds into the watch, moved the deadline, did a final poll and exited with status 0 after 5 minutes 45 seconds (16,596 tokens). The agy account had reached its quota during the test (agy 1.4.9 ended with `RESOURCE_EXHAUSTED`), so for agy only the mechanism is verified: a stub `agy` received the note intact as the `-p` argument, the tab logged `cli-exit` only after the stub's foreground waits, and claude's command is unchanged.

## Updates

With **Check for updates** on (the default, `"CheckForUpdates": true` in `config.json`), BoosterAI asks `https://api.github.com/repos/solwation/booster-ai/releases/latest` in the background at start, when the main window is activated and every five minutes while it stays active; an inactive or minimized window never checks. The last successful check is saved as `"LastUpdateCheck"`, and no check is made within five minutes of it, so at most 12 calls an hour stay well inside the 60 unauthenticated calls an hour that GitHub allows. Pre-releases and drafts are ignored, and the release tag is compared semantically with the app's own version (release builds get it from the tag, `-p:Version=${tag#v}`). A network error or an unexpected answer shows nothing; the next minute tick or activation tries again.

When a newer release exists, a bar above the projects says *Version X is available* with three choices:

- **Update** downloads the archive for this platform (`BoosterAI-<version>-win-x64.zip` or `-linux-x64.tar.gz`) and `SHA256SUMS` from the release, refuses the archive unless its SHA-256 matches, and extracts only the executable, next to the installed one as `BoosterAI(.exe).new`. A small helper script then takes over and BoosterAI exits. On Windows it is a hidden PowerShell script (`%TEMP%\BoosterAI-update-<version>\update.ps1`, no window); it waits for BoosterAI to exit, moves the old exe aside, moves the new one in (and puts the old one back if that fails) and starts BoosterAI again. On Linux a detached bash script waits the same way and renames the new binary over the old one. The helper writes `updated` or `failed: …` to `update.log` next to `config.json`. Tabs already open keep running, but the new instance does not watch them; clicking *Update* is the confirmation.
- **Later** hides that version for a day (until the app restarts); a newer release shows at once.
- **Skip this version** saves it as `"SkippedVersion"` and does not offer it again; a later release is offered as usual.

Only a copy in the location the installers use updates itself: `%LOCALAPPDATA%\Programs\BoosterAI\BoosterAI.exe` on Windows, `~/.local/bin/BoosterAI` on Linux. Anything else (a development build, `dotnet run`, another folder, a non-x64 machine) shows the bar with **Open the releases page** instead, as does a failed update. The Linux self-update replaces only the binary; the menu entry and icons from `install-linux.sh` stay as they are. The checksum comes from the same release as the archive, so it protects against corrupt or truncated downloads, not against a compromised GitHub release.

## Watching the tabs

After **Start**, BoosterAI stays running and shows a status per tab: *Starting…*, *Running*, *Watching* (Run once only: a turn ended and the CLI waits), *CLI exited (code)*, *CLI not found*, *Did not start*, *Tab closed* or *Lost*. The window minimizes to the taskbar, so the status is one click away. Closing the window quits BoosterAI. On Windows there is also a tray icon (Windows may tuck it behind the ^ arrow) whose menu shows the window or quits. Linux gets no tray icon, because many desktops (plain GNOME, for example) have no tray. A tab that has closed or whose CLI has exited gets a restart button. The button starts the same AI, model and orchestra choice. If the CLI exited while the tracked shell remains alive, it queues `RestartScript` through `QueueNext` and runs it in that same tab, preserving the title, track and log. The next `cli-start` changes the status back to Running. This also applies to Continue and Run once, regardless of selections edited since launch. PID and `/proc` start time must match; a closed or reused PID is never treated as a live shell. Tabs opened by older builds without the idle-shell restart capability use the closed-tab fallback.

For a closed or lost tab, Windows keeps `wt -w <session> new-tab`. Linux deliberately opens a new window: Ptyxis `--tab` and gnome-terminal/xfce4-terminal `--tab` select an active/last window, and BoosterAI has no verified target for the session's window. Konsole's `--new-tab` also lacks a verified session target, so each call uses `--separate`. Kitty, wezterm and xterm likewise keep their new-window behavior. This prevents a restart from entering an unrelated terminal window. A batch of closed tabs restarted together shares one fresh window in Ptyxis, gnome-terminal and xfce4-terminal; Konsole and the other terminals use separate windows. If the session window is gone, the same fallback applies. `--dry-run` prints the explicit join-request fallback for every terminal.

**Continue an ended conversation.** Beside the regular restart button, a separate continue icon reopens an ended or closed interactive AI tab with its original choices and the latest conversation in its directory: `claude --continue`, `codex resume --last` or `agy --continue` (supported by the installed agy CLI's `--help`). It sends no initial prompt, including `/orkester`. The tooltip and status say that the conversation is continued. This is explicit each time; regular restart and **Start** still start fresh. Plain shells and **Run once** tabs have no continue button: Run once's restart deliberately starts another orchestra pass. The CLI chooses the latest conversation, not a per-tab conversation ID; tabs sharing a directory can therefore continue each other's conversation. Use separate directories when their histories must stay separate. If there is no saved conversation, the CLI reports that in the terminal.

**Changing the AI or model of a running tab** shows the restart button too, with the status *Running – new choice* and the tip *Restart the tab with &lt;llm&gt; / &lt;model&gt;*. The restart happens in the same tab: BoosterAI queues the new command in the session directory (`tabN.next`), then stops the tab's foreground process group, which is the CLI and never the shell. The tab's chain then runs `bs_next` from `tab-lib.sh`, which starts the queued CLI and logs it like the first one. After a CLI exits, `bs_shell` retains that chain around the ordinary interactive shell. It records the idle child shell's PID and start time; a queued restart wakes only that child with HUP (interactive bash ignores TERM), then the original parent consumes `bs_next` again. A delayed wake cannot signal a new CLI that already consumed the queue. Exiting the idle shell normally still closes the tab. A model change on `claude` or `codex` keeps the conversation (`claude --continue --model X`, `codex resume --last --model X`). A new LLM, agy or a Run once tab starts fresh. Changing back to the running choice removes the button.

The status shows *Running* while terminal output is arriving and *Idle* after 60 seconds without output. Successful CLI exits also show *Idle* while the shell remains open; failures and closed tabs keep their separate states. Tabs started before output timing was available show *Activity unknown* until they are restarted. Interactive `claude` tabs additionally use `--settings tabN.claude.json` hooks to report when a prompt starts and a turn ends. The `Notification` hook is not used, because it also fires for a permission prompt in the middle of a turn. If the CLI is working, the restart asks first: **Restart now** interrupts the turn, and **Restart when idle** makes the row wait (*Waiting for idle…*, a second click cancels) until the next *idle*. An idle `claude` restarts without asking.

**Tabs that already run.** Each started tab saves its choices next to its log (`tabN.tab.json`). When BoosterAI starts, for example after an update, it looks through the session directories for tabs whose shell is still alive (same PID and start time in `/proc`, no *exit* in the log). Each one is matched to the configured tab with the same name and directory and is watched again, with status, restart and in-place restart, and the status line briefly says how many running tabs were found. That startup notice disappears when the first recovered tab changes state (for example its CLI exits or the tab closes), a new launch or restart starts, or another status replaces it. A delayed recovery lookup never overwrites a newer status. If the choice has changed since that tab was started, it shows *Running – new choice*. **Start** opens only the chosen tabs that are not running: the button counts those, says *All chosen tabs are running* when there are none, and opens new tabs in the window of the newest session it found. A session older than two days is kept while one of its tabs still runs.

When something unexpected happens (a tab closes, does not start, or its CLI exits with an error), BoosterAI shows a system notification. On Windows this is a toast. On Linux it uses `notify-send` when that is installed. In *Settings* you can turn **Notifications** off, and you can choose **Close after Start** to get the old behaviour back.

How it works: each Start creates a session folder (`%LOCALAPPDATA%\BoosterAI\sessions\…` on Windows, which WSL writes to through `/mnt/c`, or `~/.local/share/BoosterAI/sessions/…` on Linux) containing a small `tab-lib.sh`. Each tab's shell sources that script, and it appends `start` (PID and start time), `cli-start`, `cli-exit rc=N` and `exit` to the tab's log. Interactive commands run through `script`, which records their output timing (the activity) and the output itself for the status popup (see below). The wrapper keeps `~/.bashrc` aliases and shell functions available. The app polls the logs every 2 seconds. A shell that is gone without logging `exit` (for example after `wsl --shutdown`) counts as *Lost*. Windows detects this through `\\wsl.localhost\<distro>\proc`. Session folders older than two days are removed.

**Status popup.** Hovering a tab's status (dot and text) shows the status tip, as before, and while the tab's CLI lives (*Running*, *Idle*, *Activity unknown*, *Watching*) the last 20 lines the tab shows, in monospace and updated every second while the popup is open; nothing is read while no popup is open. For a closed, lost or not started tab, or an exited CLI, the popup only says that no output is shown. Tabs started by an older BoosterAI have no capture and say so. How it works: `tab-lib.sh` appends what `script` records (`--log-out` into a process substitution, `bs_cap`) to `tabN.out` in the session folder; a Run once tab's `bs_stream` appends the formatter's lines and the exit line the same way. A small loop beside the writer (`bs_trim`, every second) keeps it bounded: past 128 KiB, the file's last 128 KiB move to `tabN.out.1` and the file is emptied (the writer appends, so it carries on at the new start), so a tab keeps roughly 256 KiB at most. The loop also writes the tab's terminal size (`stty size`) to `tabN.size`. The capture is removed when a new CLI starts in the tab, when the tab's shell exits and, for a tab found *Lost*, by BoosterAI; whole session folders go after two days as before. Nothing is stored in a project. To show the text, BoosterAI replays the tail on a small virtual terminal at that size (`TerminalText`: cursor moves, erase line/screen, insert/delete, scroll regions, the alternate screen, autowrap; colours and titles are dropped), because the TUIs of claude, codex and agy redraw their screen in place and stripping escape codes alone would show every intermediate frame. The tail may begin in the middle of a redraw, so the result is the best reading of the latest frame rather than an exact copy; lines wider than 100 characters end in "…" and runs of blank lines collapse to one. The popup has a fixed size, so updates do not move it.

Known limit: when you close a Windows Terminal window that holds several tabs, WSL may keep their shells alive for up to about a minute, so *Tab closed* can appear late.

`--screenshot` shows sample statuses and renders the window headless, so nothing appears on screen (see [Development](DEVELOPMENT.md#screenshots)).

**Ending the day.** **Close all** asks first, then interrupts each running AI's current turn and continues its latest conversation in the project directory with a request to save, commit and push completed work and stop. It uses `claude --continue -p`, `codex exec resume --last` or `agy --continue -p`; it sends no new orchestra prompt and adds no permission bypass. Live interactive CLIs get the instruction even when their output is idle: output silence cannot establish that they have no unsaved work. Shell-only tabs, exited CLIs and Run once tabs already Watching close immediately. A separate token in the tab log identifies the save turn, so an earlier turn ending cannot close the tab prematurely. The progress dialog shows each tab saving or closed, offers **Force close** throughout, and highlights a 10-minute timeout. A failed/denied save leaves its terminal open for inspection. **Cancel** stops further automatic closing; save turns already started may finish, and closed tabs stay closed.

Continuing selects the latest conversation per AI and directory, so two watched tabs sharing both are left open with an explanation instead of choosing a conversation implicitly. Directory aliases such as symlinks and sessions opened outside BoosterAI can still make “latest” ambiguous: save those manually. Force close stops each recorded shell's foreground process group and descendants, checking `/proc` start times before signals to avoid reused PIDs. A supported shell first gets USR1 to return success; legacy or surviving shells get HUP and then KILL after a short grace period. It never kills a shared terminal server or unrelated window. Newly opened tab shells advertise a USR1 close handler (and handle HUP as a normal close) and return exit code 0 after their foreground children are stopped, so normal terminal exit handling can close them. Windows tabs always select the private BoosterAI profile with `closeOnExit: "always"`, including at default zoom, to close even after forced termination; the last such tab closes its window. Older tabs already open before this support, manually added tabs, Linux keep-open preferences and real Windows Terminal window closure have not been verified here: the full window-closing acceptance remains open until checked on Windows. No window is closed by a guessed title or a shared terminal-server PID. Tabs from older versions without a verifiable shell remain open for manual handling. Saving and pushing are requests to the CLI: denied tools or its own report may still require manual action.
