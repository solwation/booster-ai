# Details

How BoosterAI works, per platform and per feature. For the overview see the [README](../README.md).

## How it works per platform

| | Terminal | Where tabs run |
|---|---|---|
| Windows | Windows Terminal (`wt.exe`), a main tab and optional subtabs per project with colour and title | The WSL distribution you choose (default `Ubuntu`), in your Windows folder (`C:\…` opens as `/mnt/c/…`) |
| Linux | `ptyxis`, `gnome-terminal`, `konsole`, `xfce4-terminal`, `kitty`, `wezterm` or `xterm` (chosen or auto-detected) | Locally |

Settings are stored in `%APPDATA%\BoosterAI\config.json` on Windows and `~/.config/BoosterAI/config.json` on Linux. A project entry is just a name and a directory, for example `C:\Projects\webshop` or `~/webshop`.

`BoosterAI --dry-run` prints the commands that Start would run, without opening anything.
The app follows the system's light or dark theme; `--theme light` or `--theme dark` overrides it.

## Multiple tabs for one project

Choose **⋯** (*More options*) at the far right of a project's row on the main page, or right-click the row, and choose **Create subtab**; the same choice on a subtab's row adds a sibling in its project. The new subtab appears last in its group with its name selected, ready to rename. Its new row shares the project's folder without adding another project in Settings. Edit the subtab's name directly on the main page, then choose its own AI CLI, model, start command and Run once settings. The initial choices copy the main tab; later changes are independent. A Claude project also has an **Advisor** choice below its Agent and Model fields (hidden for other agents), saved as `Advisor` in the config. The row shows only while the **Advisor** switch at the top right, left of Settings, is on; the switch appears while at least one project runs Claude (a Claude subtab alone has no row: the advisor is chosen on its project) and is saved as `ShowAdvisor`, off by default. A project with an advisor chosen keeps its row with the switch off, so an active choice is never hidden, and a config with such a project starts with the switch on; the switch changes only what is shown, never what is saved or launched. The row applies to the project tab as well as its Claude subtabs; the scope is stated beside the choice. *Off* is the default, including old empty or *Standard* values. It applies `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1` only to the Claude command/runner, so a saved Claude advisor cannot activate unexpectedly; no global settings are changed. This also makes `/advisor` unavailable in that process: choose a model in BoosterAI and restart the tab to enable it. Explicit saved model choices are retained. The opt-out also covers restart, Run once and the save-and-close turn. Invalid or disallowed pairings use the same opt-out instead of inheriting a saved advisor. To avoid a doubled token bill the choices are Opus and Fable only, and the advisor is passed only when the tab's model is explicitly Sonnet or Haiku (an Opus/Fable, *Standard* or custom model gets a warning next to the choice and no `--advisor`; subtabs are checked with their own model). Otherwise the value is passed as `--advisor <model>` on start, restart and Run once, and its subtabs inherit it. Changing it on a running tab marks the tab as changed, and an in-place restart continues the conversation like a model change. Each checkbox selects that tab alone: an unticked main tab does not disable its selected subtabs. Unticking a running tab closes it (#272) the way **Close all** does, for that tab alone: an agent saves, commits and pushes its work and exits, a shell closes at once. A resting tab closes without a question; one that is starting, on a turn or whose agent reports *working* asks first (**Save and close**, **Force close** or **Cancel**, which keeps it ticked and running). Only that row closes: unticking a project leaves its running subtabs open, and the question names them. If the tab cannot close safely (for example two open tabs share an agent and folder) or takes over 10 minutes, its progress dialog opens with **Force close**. A tab that is not running only leaves the next Start, as before.

**Model memory per agent (#257).** A tab remembers the model it last used with each agent, and with each account where an agent has several (#194), so switching the Agent box away and back restores it instead of the default. A level or variant that is part of the model id (for example `gemini-4-argon-high`) is restored with it. The memory is saved in the tab's config entry as `ModelMemory` (key `agent`, or `agent/accountId` for a non-default account; absent until the tab has switched agent or account), so it follows the tab when it is moved, copied or imported, and old configs without it load as before. A remembered model the agent no longer offers is ignored and the usual default applies (a model valid for both agents is kept, else *Standard*); nothing the agent does not offer is ever remembered. Changing the memory is part of the ordinary tab choice save, never a separate unsaved state. A subtab starts as a copy of its project's choices including this memory, after which it has its own, like its other choices.

On a fresh Start the order is the main tab, its selected subtabs, then the next project's group. Drag a project's grip (the dots left of its checkbox) to move its whole group, or a subtab's grip to reorder it among its siblings. Without a mouse, focus a row (its grip takes keyboard focus with a visible ring) and press Alt+Up/Down: the row moves one step among the same peers and the order is saved at once; a list with the focus keeps Alt+Down for opening itself. Choose a row's **⋯** button (Enter or Space when it has the focus), right-click the row or press the context-menu key for the row menu: **Create subtab**, **Rename…** (also **F2** on a focused row, #258), **Move up**, **Move down**, **Show in terminal** (Windows, #253), **Start**, **Restart**, **Continue conversation**, **Open in Explorer** (*Open in the file manager* on Linux) and, on a subtab, **Remove subtab**. **Rename…** turns the row's name into a box with the name selected: Enter saves, Esc cancels, and leaving the box saves a valid name. A name that is empty, contains `;` or is already used by another project (for a subtab: by another subtab of the same project), ignoring case, is not saved: Enter keeps the box open with the reason in red and in the status line, and leaving the box drops it. The new name is written to `config.json` at once like a rename in Settings and shows in the row, the status texts and the subtabs' *Subtab of* label; a closed tab is named at its next start. An open tab, in Windows Terminal or in a Linux terminal that accepts title escapes, gets the new title at the next status poll (about two seconds) without a restart or a focus change, and its shell keeps it at later CLI starts, exits and prompts (#281); open Windows Terminal tabs are found and ordered by either the name they were started with or the new one (#254). A project with subtabs and its subtabs form one group card (#196): a faint tint and a thin outline in the project's colour, with the colour stripe running down the whole card. Nothing is indented and there is no expander; every subtab is always shown, and a project without subtabs looks like a plain row. Besides the colour, a subtab has an editable name and a × where the project has its folder icon. Dragging a project shows the drop line at the edge of the whole group, where it lands; a subtab's line stays inside its card. On Windows the open terminal tabs follow the rows: a tab started, restarted or continued into the open window is put at its row's place, and reordering rows moves their open tabs to match (see [Terminal tab order](#terminal-tab-order), #254). On Linux, open tabs are not moved: newly added or reopened tabs open where the terminal app places them. The stored group order applies the next time the group starts together. A subtab can be removed with its × or **Remove subtab** after its terminal has closed; while it is open both are inactive and their tooltip says to close the terminal tab first. An exited CLI with an open idle shell still belongs to that tab. Removing a project in Settings removes its whole configured group, just as removing a project previously removed its one configured tab.

The config keeps projects in `Tabs` and each project's extra rows in `SubTabs`, in launch order. Only the project stores the folder; child directory fields are saved empty and resolve to the current project folder. `Expanded` is kept for compatibility and ignored: a config saved when groups could be collapsed now shows all its subtabs, and the value is written back unchanged. Old configs remain single main tabs with all their choices intact. Each configured tab acquires a persistent `Id`, also saved in its session metadata, so equal names or shared folders do not confuse status, in-place restart or recovery after an app update. Session metadata from before IDs falls back to matching a main tab's name and directory. Each subtab has its own log, PID and lifecycle; global Start, Restart all and Close all include all subtabs. The CLIs' **Continue**/`--last` operations select a conversation by directory, not by terminal tab. When another row in the same group uses the same CLI (or still runs it), **Continue** is hidden and changing a model restarts with a new conversation, as its tooltip explains; it cannot silently resume a sibling's latest conversation. Close all leaves ambiguous same-CLI/same-folder agents for manual save or force close as before.

## Accounts per agent

An agent that can point at another configuration directory can have several accounts, for example a private and a work login. Claude Code uses `CLAUDE_CONFIG_DIR` and Codex `CODEX_HOME`; each directory holds its own login, settings and conversations. Antigravity (`agy`), Aider, Open Interpreter and OpenHands document no such variable, so they only have their default account and show no account choice.

Settings → **AI agents** → Claude or Codex → **Accounts** lists the agent's accounts. **Default** is the agent's usual directory (`~/.claude`, `~/.codex`); it is always there, cannot be removed, and sets no variable (it can be renamed, see below), so configs and tabs without accounts start exactly as before. **Add account** creates an account with its own directory derived from the name (`~/.claude-work` for *Work*, with a number when taken) in the Linux the tabs run in (WSL on Windows). Renaming keeps the directory and every tab that uses the account. **Log in** opens a visible tab that exports the variable, creates the directory and runs the agent's login (`claude auth login`, `codex login`), then leaves a shell with the variable set; on the default account it removes an inherited variable instead, so the login goes to the agent's usual directory (#193). Removing an account only removes it from BoosterAI: its directory and login stay on disk, and the tabs that used it switch to the default account. A new account starts without the default account's user settings, such as `~/.claude/CLAUDE.md`, `settings.json`, skills and plugins, or Codex's `config.toml`; copy what you need into the new directory.

Every account row shows its login status, also the default account (#192): *Logged in as name@example.com · Organisation* (Claude), *Logged in with ChatGPT* (Codex), *Not logged in*, or *Unknown status* when the check fails or takes too long. The identity in the status line makes the default account recognizable without renaming it, and the button (also on the default account) reads **Log in** until the account is logged in and **Log in again** after. The status comes from `claude auth status --json` and `codex login status`, run in the tab's login shell (`bash -lic`, through `wsl.exe` on Windows) with the account's variable set for a non-default account and none for the default, in the background with a limit of about 10 seconds; an account whose directory does not exist yet counts as not logged in, and any other failure (command missing, timeout, unreadable output) is *Unknown*, never *Not logged in*. It is checked when the Accounts page opens and again when the Settings window is activated, so a login in the tab BoosterAI opened shows when you return; an account that is already being checked is not checked twice. The email address is only displayed: it is not saved, logged or written to the config. Screenshots and tests use invented statuses and never run the commands.

Every account row also shows the plan limits BoosterAI could read for the account (#199): a thin bar and *37 % used · resets in 4h 20m (14:20)* for the short window (*5 h*) and the *Week*, credits for Codex (*Credits: 120*, *unlimited* or *none*), and *updated 8m ago* for when the agent reported the values (see [Times](#times)). A window without a value, or an account nothing has been read for yet, shows *Unknown* without a bar, never a guessed 0 %; a window that was read but whose reset time has passed since shows *Probably reset* (#214). The values are read when the Accounts page opens and when the Settings window is activated, like the login status, in the tab's login shell (`bash -lic`, through `wsl.exe` on Windows) with a limit of about 10 seconds. The shared windows come from local files. BoosterAI reads no account credentials or tokens. The read prints one projected JSON line (window percentages, reset times, window lengths, credits, time), never file contents. It needs `python3` in that Linux; without it everything is *Unknown*.

**Codex resets (#274).** Codex can grant earned rate-limit resets. For each Codex account BoosterAI reads how many are available through `codex app-server` (`account/rateLimits/read`, `rateLimitResetCredits.availableCount`) with the account's `CODEX_HOME`, at most every 5 minutes, and shows *2 resets left* beside the credits; nothing while the count is unknown. When the account's usage is used up (Codex says ordinary usage is not allowed or a limit was reached, or a window is at 100 %) and a reset is available, the row shows **Use reset**. It first asks *The account Work has 2 resets left. Do you want to use one now?*; **No** changes nothing, **Use reset** redeems exactly one (`account/rateLimitResetCredit/consume` with a new idempotency key), then reads the count and limits again. Success is shown on the row and in the status line; a failure on the row and in the error banner, whose **Try again** repeats the same attempt (same key), so it never uses a second reset. BoosterAI does not type `continue` into a Codex tab: Codex does not write a stopped turn's usage-limit error to its session log, BoosterAI does not know which session a Codex tab runs, and a Codex tab gives no reliable idle signal, so the user types `continue` in the tab that stopped. Claude Code and AGY expose no readable count or redeem interface, so their rows show nothing. Each read or redemption starts the app-server for at most about 25 seconds and stops its whole process group afterwards. A Codex tab's status popup shows the same count under its plan limits (*2 resets left*, #285), from this reading, so hovering starts no app-server; when the quota is used up and a reset is left it adds *The quota is used up. A reset can be used from Accounts.* Nothing shows while the count is unknown or for other agents.

The main window shows the same reading without reading more (#200, #205, #206): one reading per account/agent is shared between Settings and the main window, read when the main window is activated or a monitored tab changes activity (at most every 5 seconds), every 30 seconds while it is visible, and once at start, for the agents that tabs use (Claude, Codex and AGY). Installed Claude, Codex and AGY agents that no tab uses are read too, with all their accounts, at start and then at most every 5 minutes (#214), so the Agent list also knows an account no tab uses; before the first setup check every one of them counts as installed. In the Agent box's dropdown, each Claude, Codex or AGY entry with a known window ends with the higher of the 5 h and weekly use (*62 %*); from 80 % it also has a warning icon. The closed box shows two thin usage meters along its bottom edge for the tab's account/agent (#202, #206, #219): the 5 h window on top and the week below, each filled to its own use, so both limits are visible at once; the same two meters sit under the agent name in every dropdown entry. From 80 % a meter turns to the warning colour and a small warning icon appears beside the agent (accessible name *close to the limit*), so colour is never the only cue. A window without a known level (*Unknown*, or *Probably reset* after its reset time, #214) is an empty, muted track, never a guessed 0 %; a limit-capable agent or account with no known window shows two empty tracks. The meters' tooltip lists both windows with their use and when they reset, and *updated 8m ago*; the accessible name names both windows with remaining, used and reset time (*5 h: 38% left, 62% used, resets in 2h 37m (18:20); Week: ...*). The meters lie over the box's padding, so neither the box nor the row grows, and every row's tracks have the same length; the list entries are about 6 px taller. Pressing the meter opens the box. On active, idle, watching and starting tabs with a known limit, the compact **Status** column shows the remaining percentage of the tightest window beside the status dot (*38%* / *38 %*, #207, #209), in the warning colour from 80 % used; the dot's accessible name has the full status with it (*Running · 38% left*). *Unknown*, non-limit agents and closed/error rows show no percentage. The tab's status popup has a small *Plan limits* table for claude, codex and agy tabs (#210), headed by *updated 8m ago*. Each window has its own row: the label (*5 h*, *Week*), a meter of the **remaining** share, the remaining percentage in bold (*63% left*), the used percentage muted (*37% used*) and the reset time (*resets in 2h 37m (18:20)*), so it is clear which is which. A missing window shows only *Unknown*, without a meter. From 80 % used, the row's meter and percentage take the warning colour and a warning icon, and its accessible name ends with *close to the limit*. Agents without limits and *Unknown* accounts show nothing.

**Plan-limit percentages (#217).** Every percentage of a plan limit (status column *N % kvar*, the status popup's table, the Agent box's chip, meter name and list, Settings → Accounts and the low-quota warning) comes from one formatter, `LimitPercent`. Whole numbers are shown, except when less than 3 % is left (`DecimalBelow`): then one decimal, in the UI language's separator (*99,3 % använt* / *0,7 % kvar*, English *99.3% used* / *0.7% left*). 100 % used / 0 % left appear only for a reading of 100 or more; a reading below 100 is clamped to at most *99,9 % använt* / at least *0,1 % kvar* (used is rounded half away from zero, remaining is 100 minus the displayed used, so the two always add up). Exactly 97 % used is still whole (*3 % kvar*), 96.99 shows *97* / *3*. The low-quota check compares the displayed remaining value, so *0,7 % kvar* is below a threshold of 1 and the text never contradicts the threshold. The bars' fill uses the raw reading.

**Low-quota warning (#211).** Settings → General has **Warn when quota drops below [N] % left** (`QuotaWarn`, on by default like *Notifications*, and `QuotaWarnPercent`, default 5, allowed 1–50 in `config.json`). When a Claude, Codex or AGY plan window (*5 h* or *Week*) of an account has fewer than N % left after a reading, the main window shows a quiet bar among the banners (no dialog, no focus change) such as *claude (Work), 5 h: 4% left, resets in 1h 37m (17:40)* (account name only when the agent has several accounts; reset time as in [Times](#times)). The percentage compared is the rounded one shown, so exactly N % is not below. Accounts that no tab uses are checked too (#214), so a maxed account warns once even without a tab. Each agent, account and window warns once: it warns again only after the window has reset (a different reset time) or after a reading with N % or more left. Unknown readings and windows that have already reset change nothing; a window that is already below the threshold at the first reading warns once. Closing a bar does not re-arm it, and at most four bars are shown (a newer one for the same window replaces the older). Turning the setting off shows no bars and keeps no history.

**Quota notifications (#239).** The same setting also sends each low-quota warning as a system notification (the toast on Windows, notify-send on Linux; clicking it shows the main window as for other notifications), once per window like the bar, and only for agents and accounts a tab has chosen (#238). When a window that warned (below N %, which includes 0 % left) then shows a reading at or above N % or a reset window, one more notification says *Nu har din claude (Privat) fått fler tokens: 5 h, 90 % kvar* (agent, account when several, window, remaining share), once per recovery. A window that is merely past its reset time (*Probably reset*) does not notify until a reading confirms it. `QuotaWarnings.Evaluate` decides both and `MainViewModel.QuotaNotify` sends them, so tests capture the text without showing anything.

**Save notice to running agents (#275).** Settings → General has **Ask running agents to save their state when the quota has [N] % left** (`QuotaSaveNotice`, on by default, and `QuotaSaveNoticePercent`, default 1, allowed 1–50), independent of the low-quota warning. When a reading shows a *5 h* or *Week* window of an account with N % or less left (here exactly N % counts, since readings in whole percent would jump from 1 % to 0 %), every running tab and subtab whose CLI was started with that agent and account gets one short English note: *The claude account of this tab has about 0.8% of its 5-hour quota left (it resets in 1 h 10 min). Work stops when it runs out. You may want to save your state now: commit and push what is complete and write down the next steps. Whether and how is up to you.* The time is given as a duration, since the agent's time zone is unknown. BoosterAI interrupts, types and closes nothing; what the agent does is its own choice. It is sent once per agent, account and window instance, and again only after the window has reset or risen above N %; a tab started later in the same window gets none. The status line says *claude (Work), 5 h: 0.8% left. Asked Atlas, Atlas-api to save their state.* (and *Skipped …* for tabs that could not receive it), the row's status tooltip and status popup add *Save notice sent to the agent today 14:20*, which becomes *…, read by the agent today 14:22* once the agent's side has taken it, or *Save notice not sent today 14:20: <reason>*. While the main window is unfocused and *Notifications* is on, one system notification (*Quota nearly used up*) says the same, as for a changed agent status (#270); a focused window shows only the status line. Every sent or skipped note is also recorded in the session folder's `quota-notices.log`.

**Switch to an equivalent model when the quota is used up (#279).** When a reading of an account that a running AI tab uses shows a window (5 h or week) 100 % used, no resets left (Codex's earned resets, #274; claude and agy have none) and the reset more than 2 h away (`ModelSwitch.MinWait`), BoosterAI offers to switch the tab to an equivalent model on another agent or account with quota left: *"Kvoten för {konto} är slut till {tid}. Byta {flik} till {agent} · {modell}, som har {x} % kvar?"* with **Byt** and **Avbryt**. It goes by the account's quota, not by whether the tab has stopped (a Codex stop is not visible in its log, #277). When the main window is unfocused a notification is shown too, and the question appears when the window is activated (a click on the notification does that). **Byt** changes the tab's agent, account and model and restarts it in place (the changed-model restart of #38) with the English first prompt *"Continue where the previous agent left off. Read the repository state, recent commits and any notes or issue comments it left before changing anything."* The switch only happens while the tab is idle: its activity is Idle or the agent's own status (#248) is idle, done or blocked. A working tab waits, its row says *"Byter till {agent} · {modell} när fliken är ledig"*, nothing is interrupted, and ↻ cancels the wait and restores the earlier choices. When the activity is unknown (no hooks, output timing or status, as in some Codex tabs) Byt asks *"Aktiviteten är okänd, byt ändå?"* first. No save prompt is sent before the switch: #275 already asked the agent at about 1 % left. Run once tabs, tabs with unsaved choice changes and tabs already waiting are skipped.

Equivalent models (`ModelSwitch.Tier`, from the catalog of #265: built-in ids plus what `ModelDiscovery` found). The target model is the first id of the same tier in the target agent's catalog order.

| Tier | claude | codex | agy |
| --- | --- | --- | --- |
| Top | `claude-opus-*`, Standard | `*-sol`, `*-astra`, Standard | `gemini-*-neon-*`, `gemini-*-hydrogen-*`, `gemini-pro-*`, `claude-opus-*`, Standard |
| Mid | `claude-sonnet-*` | `*-terra` | `gemini-*-carbon-*`, `gemini-*-argon-*`, `claude-sonnet-*`, `gpt-oss-*` |
| Small | `claude-haiku-*` | `*-luna` | `gemini-*-flash-*` |

`claude-fable-*` (its own Fable window) and other ids have no tier, so no switch is offered. Targets are claude, codex and agy accounts (BoosterAI reads quota only for those) that are installed according to the last setup check, not known to be logged out (an unchecked login counts when the account has a reading) and have quota left in every window of their latest reading; the one with most left wins. Each tab is offered or switched at most once per quota window, and never back to an account it left before that account's window has reset, so two exhausted accounts cannot ping-pong. With the restart the new conversation starts fresh; a tab with a start command gets the continuation prompt instead of its command.

**Experimental: automatic switch (#279).** Settings → General → *Experimentella funktioner* has **Byt modell automatiskt när kvoten är slut** (`AutoModelSwitch`, off by default). Turning it on asks *"Detta kan förbruka dina tokens snabbare än planerat. Experimentell funktion."* with **Slå på** and **Avbryt**; Avbryt leaves it off. When on, the switch is made without a question (still only while the tab is idle, waiting otherwise) and a notification is always shown, also when BoosterAI has focus: *"{flik} bytte till {agent} · {modell}: kvoten för {konto} är slut till {tid}."* A tab whose activity is unknown is never switched automatically; it gets the question instead.

- **Delivery path, per agent.** *claude* and *codex*: through the [tab status channel](#tab-status-channel). BoosterAI writes `tabN.notice`, and the tab's MCP server adds it to the result of the agent's next `boosterai_status` or `boosterai_ask` call, which the agents make before each new step; so the note reaches a running agent between two steps, in its own context, without touching the terminal. A tab whose agent is idle at its prompt reads it with its next turn. *agy, aider, openhands, interpreter* and the shell: skipped and recorded (*agy has no safe way to receive it*). They get no MCP server or instruction from BoosterAI, so nothing would read the note mid-session. Also skipped: tabs started with the status channel off and Run once tabs, which have no MCP server.
- **Not chosen.** Typing into the terminal (`bs_pty`, as auto-clear does) is safe only into an idle claude, where it would start a new turn and use the last of the quota, and it is blind for codex and agy, whose turns BoosterAI cannot see end. A Claude Code hook (`additionalContext` from `PostToolUse`) would reach claude after every tool call, but serves claude only and adds a second mechanism beside the channel, which already reaches both claude and codex.
- **Limits.** The note arrives at the agent's next status call, not instantly; an agent that ignores the instruction to report its steps gets it only when it next calls a channel tool. Codex credits have no total to take a share of, so only the 5 h and weekly windows count. Tabs that started before this version run the older MCP server and do not read notes until they restart.

**Low-quota warning, continued.** The check runs on the same readings as the Agent boxes and the Accounts page, so it follows their refresh cadence and only covers accounts BoosterAI can read.

**Accounts without a tab and old readings (#214).** Every Claude, Codex or AGY entry in the Agent list says something: the level when a window is known, otherwise *Unknown* (muted) whose tooltip says why (*Plan limits: unknown.* and how the agent's limits are read, as below). A reading keeps its level until the window's own reset time, however old it is, because the use can only have risen since: an account that hit 100 % of its week yesterday still shows *100 %* with the warning icon (accessible name *limit reached*) today, even when no tab uses it. A reading an hour old or more also shows its time beside the level in the list (*100 % · yesterday 18:10*, see [Times](#times)), and the tooltip has *updated yesterday 18:10*. Once a window's reset time has passed, its old level no longer applies: that window shows *Probably reset* (*Troligen återställd*) in the Accounts page, the tooltips and the status popup's table, and when no window is known any more the Agent list entry shows *Probably reset* with a tooltip giving the last known level and its time. A reset window never triggers a quota warning. A new level appears with the agent's next reading (for Claude and AGY, the next reply/start of a BoosterAI tab with that account; for Codex, its next turn on this machine). The clock alone moves an entry from its level to *Probably reset*: the list follows on every refresh, also between the 5-minute reads.

**Weekly quota for the selected model (#230).** When a Claude tab or subtab selects Fable, BoosterAI asks the Claude CLI for its structured `/usage` report. The CLI uses that account’s sign-in and queries Anthropic without a model turn. BoosterAI caches the Fable window in memory per WSL distribution and account directory for five minutes. The tab’s weekly meter reflects that window. The status popup also lists the shared weekly window, and the compact status shows the lowest remaining share across the applicable windows. When a new reading changes a known level within 40 seconds of the app starting or its window being activated again, the compact status counts from the old to the new share with a short `(-5%)`/`(+5%)` that fades out, and the Agent box's meters slide to the new level; the last levels are kept in `limit-levels.json` beside `config.json`, so the first reading after a restart compares with what was last shown (#234). Other models use the shared weekly meter. If Claude supplies no Fable window, its meter stays unknown while the popup still shows the shared limits. The separate window is available on plans that include Fable, such as Max and Ultra or eligible Team seats. See [the Claude Agent SDK usage report](https://code.claude.com/docs/en/agent-sdk/typescript#sdkusagereport).

- **Codex:** the last `token_count` event with `rate_limits` in the newest rollout under the account's `CODEX_HOME/sessions` (the last 4 MB of at most the five newest files). Codex names its windows *primary* and *secondary*; their length decides which is the short window and which the week (some plans only report a weekly window and leave the other `null`: the short window then shows *no 5 h limit* (*ingen 5 h-gräns*) without a meter or quota warning, and the compact status uses the week; a window that is there but cannot be read stays *Unknown*, #231). Credits come from the same event. The values are as of the account's last Codex turn on this machine.
- **Claude:** Claude Code passes its shared plan limits to a status line command. BoosterAI's interactive Claude tabs get a status line in their `--settings` file (`tabN.claude.json` in the session folder, beside the activity hooks) that runs `statusline.py` from the same folder. Without one it prints nothing; `padding` and other options of your own status line are not carried over. Tabs started outside BoosterAI, or before this version, do not update the snapshot. `BoosterAI --dry-run` prints each Claude tab's settings with the status line.

BoosterAI's interactive AGY tabs get `--settings` (`tabN.agy.json` in the session folder) running `agy-statusline.py`. When you have no custom `statusLine` in `~/.gemini/antigravity-cli/settings.json`, `stack_with_default: true` keeps AGY's built-in status line while BoosterAI's script prints nothing; when you do have a custom `statusLine`, `tab-lib.sh` selects `tabN.agy-replace.json` (unless your `statusLine` sets `stack_with_default: true`) and chains your command with the same stdin (bounded to 4.5 seconds and 64 KB). Without `python3`, `tabN.agy-plain.json` (`{}`) leaves your settings untouched. AGY 1.5.17 runs the command right after it starts, before any reply, and its stdin already carries `quota` (for example `gemini-5h`, `gemini-weekly`, `3p-5h`, `3p-weekly`), so the snapshot appears within seconds of a tab's start. A tab started by a BoosterAI before 0.46.0 has no such settings and never saves the quota; agy also refuses to start when its `--settings` file is missing, so an in-place restart of such an adopted tab first writes the missing `tabN.agy*.json`. While no reading is known, a live AGY tab's status popup says why instead of showing nothing: *Plan limits: unknown – restart the tab* for a tab without the settings, otherwise *not known yet* (the status line needs python3).

The default account can be renamed per agent (for example *Private*): type the name in its row. The name replaces *Standard* in the Accounts page, the **Agent** box on the main page and the status popup. A name is never set automatically from the detected identity.

The main page chooses agent and account in one control, the **Agent** box (#194). ## Terminal window placement

On Windows, BoosterAI remembers the visible bounds and monitor of the Windows Terminal window it opens. The next session restores that placement, including maximization. Docked/Snap windows reopen with the same bounds; Windows Snap group membership and FancyZones layouts are not recreated. When the monitor is disconnected, or its work area changes (resolution, scaling or taskbar), the bounds are fitted to an available monitor's work area.

This works without changing global Windows Terminal settings. A brief bootstrap tab identifies the new window using a random handshake title, then closes automatically; the ordinary project tab names stay unchanged. A small headless BoosterAI helper watches that exact window, including after *Close after Start* or quitting BoosterAI, and exits when the terminal closes. It records changes about twice per second in `%LOCALAPPDATA%\BoosterAI\terminal-placement.json`; minimizing does not replace the last visible placement. Invalid or missing saved data and unavailable tracking fall back to the normal terminal launch. Packaged helpers run from a shared versioned copy under `%LOCALAPPDATA%\BoosterAI\placement-watchers`, so an open terminal does not lock the installed executable during an update; unused older copies are removed on a later launch. Other Terminal windows are never moved. Already-open tracked windows only get their new tabs, without having their placement reset.

### WSL optimization

WSL's default memory cap is 50% of the host's RAM. A custom cap is optional; raising it is not always an improvement when Windows applications or other virtual machines share the computer. Without an explicit setting in `%USERPROFILE%\.wslconfig`, the main window offers **Review memory …**, which opens the **Memory and context** tab.

The slider shows a bracketed, proportional suggested range with both GB limits, separate from the selected cap. The range is a cautious rule of thumb based on roughly 3/8–1/2 of total physical RAM, clamped to the slider's limits on small computers: for example, 64 GB gives **24–32 GB**. It does not measure or reserve memory for Hyper-V or other VMs. The setting is a maximum for WSL, not memory reserved immediately. All workloads still share the host's RAM.

Start at the lower end, or below the range, when Hyper-V or other VMs run alongside WSL. Try the upper end for heavy WSL builds only when other workloads leave room, and keep headroom for peak demand. The initial selection without a custom cap and **Choose lower value** both use the lower limit. An existing saved cap is retained; users can still select values outside the suggestion. A saved cap outside the slider's limits (below its minimum or above total RAM minus 2 GB) is still shown as the current value; the slider starts at its nearest end, and **Save** stays off until you move the slider. Saving writes `.wslconfig` while preserving its other sections and comments; **Restart WSL** runs `wsl.exe --shutdown` to apply the new cap. **Not now** dismisses the main-window prompt permanently. Native Linux displays system memory and explains that `.wslconfig` applies only to Windows/WSL.

Below the slider, **Return memory to Windows** shows `autoMemoryReclaim` under `[experimental]` in `.wslconfig` (not set, `disabled`, `gradual`, `dropCache`, or an unknown value as written) and recommends `gradual`, which slowly returns unused Linux page cache so `vmmemWSL` shrinks after tabs close; `dropCache` releases it at once but can slow builds. **Use gradual…**, **Switch to dropCache…** and **Remove the setting…** each show the exact lines added or removed before writing; only that key's line (and an `[experimental]` header it needs, removed again when left empty) changes, and other keys, sections, comments, line endings and a byte order mark stay as they were. The change applies after **Shut down WSL…** (`wsl --shutdown`), which ends all running tabs and agent sessions; BoosterAI never restarts WSL itself. The WSL version is read with a hidden `wsl.exe --version`; below 2.0.0, or when it cannot be read, a message replaces the write buttons (removal stays available).

Memory and context has a left-hand menu: **RAM usage**, **Memory limit**, **WSL & environment** and **Context** (auto-clear and auto-compact, see [Auto-clear when idle](#auto-clear-when-idle) and [Auto-compaction budgets](#auto-compaction-budgets)). Arrow keys move through these sections; each page scrolls independently in a smaller window. The main-window memory notice opens **Memory limit** directly. **WSL & environment** shows the configured distribution, WSL availability, the distribution used by the last check and the detected distributions. This information refreshes automatically at startup and when the main window is activated. On Linux the page explains that tabs use the local environment. Its **AI agents** link opens the shared overview for program installation, versions, manual refresh and agent settings. Alias status and definitions are only shown under **AI agents**.

While BoosterAI runs (including when hidden in the tray), it samples WSL's **resident host RAM** every 30 seconds, without starting a distribution or helper process. **RAM usage** gives the current value, separate minimum/average/maximum readouts and four labelled bars: current usage, observed history, suggested range and configured cap. All four use a shared scale from zero to the host's total RAM; the history's outlined band is minimum–maximum and its contrasting vertical line is the sample average. The suggested cap range is green, and the configured cap is a separate neutral bar. Exact values stay readable when observations fall outside the chart's scale. **About this data** explains what is measured and the history's limits.

**Change memory limit** opens the slider and guidance on their own page. The slider's selected value can differ from the configured cap until you explicitly save; observations and page navigation never change either value. The configured-cap bar reflects `.wslconfig` (or the 50% WSL default), not proof that WSL has restarted with it. Saving a cap refreshes the overview; **Restart WSL** still applies it explicitly.

The source is the summed Windows `WorkingSet64` of processes named `vmmemWSL`: resident physical memory attributed to WSL, including its kernel and cache, rather than Linux application memory alone, committed memory or swap. WSL2 distributions share a VM and its memory; the value covers WSL2 on the host, not just the selected project or distribution. Other Hyper-V VMs are excluded. Older Windows/WSL versions exposing only ambiguous `vmmem` report the measurement as unavailable instead of counting unrelated VMs. No matching process, a failed query or an outdated reading is shown explicitly; missing readings are never recorded as zero.

History stays in memory and starts afresh when BoosterAI starts. **Collected …/30 min** reports observed time between adjacent samples, excluding gaps longer than 45 seconds; the sample count makes short/partial histories visible. During an interruption the remaining recent history is still shown, but the current value is unavailable; samples older than 30 minutes are discarded. The mean, minimum and maximum describe sampled observations and can miss peaks between samples. Past usage does not guarantee future demand, so leave headroom when choosing the cap.

The [Microsoft WSL overview](https://learn.microsoft.com/windows/wsl/about) describes shared WSL2 memory, and [process working sets](https://learn.microsoft.com/windows/win32/procthread/process-working-set) explains the resident-memory metric.

See [Microsoft's WSL configuration reference](https://learn.microsoft.com/windows/wsl/wsl-config) for the memory cap and defaults, and [Hyper-V memory management](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology#dynamic-memory) for VM memory needs.

### Font size

*Font size* in the settings window zooms the CLI text in all tabs (50–200 %; saved as `"ZoomPercent"` in `config.json`, `0` = the terminal's default font size). The choice is saved as soon as it is made, not only when the window closes. In Windows Terminal it applies to new and already-open BoosterAI tabs; in the Linux terminals on the next Start. Several BoosterAI instances may run at once (e.g. one in the tray and one started from the shortcut): each save takes over settings another instance changed in `config.json` instead of writing back its own older value; the tab list is not merged.

On Windows, BoosterAI writes `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\BoosterAI\boosterai.json` (a hidden "BoosterAI" profile with [`closeOnExit: "always"`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-advanced#profile-termination-behavior), plus `font.size` as a percentage of Windows Terminal's 12 pt default when an explicit zoom is selected; it inherits your other defaults) and opens the tabs with `-p BoosterAI`; at the default size the profile remains but omits `font`, inheriting your font settings. Only BoosterAI tabs select this profile, so your other profiles are unchanged. Windows Terminal reads fragments only when it loads its settings, so when the fragment changes while Windows Terminal is running, BoosterAI adds or removes one trailing newline in Windows Terminal's `settings.json` to make it reload, and waits two seconds before opening the tabs. That newline is the only change to your `settings.json`; your settings themselves are never touched. When a zoom is chosen in Settings, BoosterAI writes the fragment and nudges a running Windows Terminal right away, so it reloads the profile, which open BoosterAI tabs may also pick up.

At normal app startup, BoosterAI also refreshes the saved profile even when the fragment already matches. While Windows Terminal is running, it briefly switches the private profile's size and then restores the latest saved choice, reloading settings at both steps. This reproduces a size toggle without changing `config.json`. Restoration is attempted even if the first step fails, and multiple BoosterAI processes serialize profile updates with a Windows mutex. This runs in the background, including after installation or an app update; dry-run, screenshots and placement-watch helpers never request it. It reapplies the profile's base font size; tab-local zoom and explicit Windows Terminal overrides remain Windows Terminal settings.

Windows Terminal layers your own `settings.json` over a fragment: a `font` (size) on the "BoosterAI" entry in its `profiles.list` (Windows Terminal adds that entry, with `"source": "BoosterAI"`, the first time it loads the fragment) beats BoosterAI's zoom. If the zoom seems to do nothing, remove `font` from that entry in `settings.json` (the profile is hidden in Windows Terminal's settings UI), or set the size you want there yourself. `profiles.defaults` is a lower layer than the fragment, so a font size there does not override the zoom. Zooming a single tab with Ctrl+mouse wheel or Ctrl+= is Windows Terminal's own and lasts for that tab only.

On Linux all tabs open as tabs of ONE window in `gnome-terminal` and `xfce4-terminal` (a single call with `--window` and `--tab` groups), and in `ptyxis` (Ubuntu 25.10+ and Fedora default; `--tab-with-profile=default --new-window` to preserve multi-tab mode and visible tab bar, then `--tab` in that window, each call waiting for the previous one; when Ptyxis is not running yet, BoosterAI turns its `restore-session` setting off until the tabs are open, because a restored session reopens the last run's tabs as plain shells in their old windows and those take the tabs; this suppression requires `gsettings`). `konsole` uses `--separate --new-tab` and a separate window per tab to avoid targeting an unrelated existing window. `kitty`, `wezterm`, `xterm` and `x-terminal-emulator` have no tabs here, so each tab gets its own window. With `auto`, Ptyxis is tried first, then gnome-terminal and the rest in the order listed.

On Linux the zoom is passed to gnome-terminal (`--zoom`), kitty (`-o font_size`, 11 pt base) and wezterm (`--config font_size`, 12 pt base); other terminals (ptyxis, konsole, xfce4-terminal, xterm, ...) have no command-line option for it and ignore the setting. `BoosterAI --dry-run` prints the resulting commands and fragment.

## The orchestra choice

[Dirigenten och orkestern](https://github.com/solwation/dirigenten-och-orkestern) lets AI agents work through a project's GitHub issues. A conductor picks issues by priority, hands them to parallel worker agents in their own checkouts, then reviews and delivers the results.

Each AI row has one **Start command** list (#255; before, an *Off / Orchestra / Orchestra, once* choice, #152). It holds *No command*, then `/orkester` at the top, set apart from the rest (where the folder has the orchestra), then the commands found for the tab's agent, folder and account, grouped under *Project*, *User* and *Plugin* with the description from each file's frontmatter. The chosen command is sent as the tab's first prompt. A row stays one line. For a row with a command, its menu (**⋯** or right-click) has **Run once** (a checkable entry, see Run once below) and **Arguments…** (a small dialog; Enter saves one trimmed line, Esc cancels; the current value is part of the entry) that apply to any command: `/review` with `#42` starts `claude '/review #42'`, and Run once makes it `claude -p '/review #42'` (#260; #255 first had them on an extra line under the row). A small marker beside the list (*1×* for Run once, *arg* for arguments) shows that either is set, and the list's tooltip spells it out. In `config.json` the choice is `"Orkester"` (the orchestra) or `"Command"` (exactly as typed, such as `/deploy` or `$release-notes`), with `"CommandArgs"` and `"NonInteractive"`; old configs keep their meaning (On is `/orkester`, Run once stays with it, and a Run once stored while the orchestra was off is dropped). A saved command that the last check did not find stays in the list, marked *Not found at the last check*, and is still sent. Projects without the orchestra show an "Install" link instead (or, when the list has other commands, an *Install /orkester…* entry that opens the same dialog), on the project row only (subtabs share its folder, #197): a dialog explains what will happen, then the AI you chose opens in a new tab and installs it, asking you about the rules before it commits anything. While no visible row can use or install the orchestra or has a command to choose (plain shells, or folders not checked yet), the column and its header are hidden and the project column gets the room. The check repeats about every 45 seconds while the main window is visible and not minimized, and when the window is activated, so an orchestra installed or removed outside the app shows up without restarting; a directory whose check is still running is skipped.

### The start command

Commands are read in the background in the tabs' WSL distribution (Linux: locally) by one hidden `bash` for all rows, with a 20-second limit, when the main window opens and is activated (at most every 30 seconds) and when a row's folder, agent or account changes. Only the command files are read; nothing is run. Per agent (checked against Claude Code 2.1.332, Codex 0.172 and agy 1.5.18):

- **Claude Code:** `.claude/commands/**/*.md` in the folder and in the account's directory (`~/.claude` or the account's `CLAUDE_CONFIG_DIR`); a subdirectory is a namespace, so `commands/docs/check-links.md` is `/docs:check-links`. User-invocable skills `.claude/skills/<name>/SKILL.md` in both places (`/name`, from the frontmatter's `name` or the folder; `user-invocable: false` is left out). Commands and skills of plugins installed in `plugins/installed_plugins.json` and enabled in the user's, project's or local `settings.json` (`/plugin:name`); a project-scope install counts only in its project. Without a `description`, the body's first line is shown, as Claude Code does.
- **Codex:** skills in `.agents/skills` of the folder, `~/.agents/skills` and `$CODEX_HOME/skills` (the account's), typed as `$name`. Custom prompts in `~/.codex/prompts` (`/prompts:name`) are not listed: the supported Codex no longer reads them.
- **agy:** workflows in `.agent/workflows`, `.agents/workflows`, `_agent/workflows`, `_agents/workflows`, `~/.gemini/config/global_workflows` and `~/.gemini/config/workflows`, typed as `/name`.
- **Aider, Open Interpreter, OpenHands:** no user-defined commands, so only *No command* and `/orkester`.

A file whose frontmatter is broken (opened with `---` but never closed, or with lines that are not `key: value`) is still listed, without a description. `/orkester` itself is never listed among the found commands. Each agent gets the command as its first prompt the way it takes one: `claude '<command>'`, `codex '<command>'` (`codex exec` for Run once), `agy -i` (`-p`), `aider -m`, `openhands --task`. Only the orchestra's Run once gets the foreground-watch note for codex and agy; other commands end with their turn. `;` and `"` in the arguments are encoded in the tab script, because Windows Terminal splits its command line on `;`.

### Reload an idle orchestra

An interactive Claude tab with the orchestra enabled shows the reload icon when its hooks report the turn complete and its terminal has been quiet for two seconds. The tooltip says **Run /orkester again in the idle session**. Clicking sends exactly one `/orkester` prompt to that existing CLI: its PID, terminal, working directory and conversation remain intact. The action is separate from restarting an exited CLI or applying a model change, and it does not add idle tabs to **Restart all**.

The tab checks the exact idle period and input-channel generation again before typing and before Enter. Recent keyboard input (including an unsent draft; see [what counts as a key](#what-counts-as-a-key)), ongoing/background work, an old status snapshot or another queued input request prevents submission. Repeated clicks cannot queue another run in the same idle period. Auto-clear and reload share one input slot; reload is not recorded as a clear and cannot be replaced by one. An already-completed auto-clear does not prevent a later manual reload.

This currently requires Claude's explicit busy/idle hooks and the new PTY input channel (Python 3 and util-linux `script`). New interactive orchestra tabs get the channel even with auto-clear off. Tabs started with an older library need one ordinary restart before reload becomes available. Run once and other CLIs retain their existing restart behavior: their current output-silence status cannot prove that a prompt is safe to submit, so no in-session reload is offered for them yet.

## Run once (non-interactive)

**Run once** in the row menu of a row with a start command (`"NonInteractive": true` in `config.json`, with `"Orkester"` or `"Command"`) starts the CLI non-interactively with that command instead of an interactive session: `claude -p '/orkester'`, `agy -p '/orkester'` and `codex exec <orkester skill or /orkester>`, or the same with your own command and its arguments. The tab shows live progress while it runs: for `claude` and `agy` the event stream (`--output-format stream-json`) goes through a small formatter in `tab-lib.sh` (`bs_stream`, uses python3 if present, otherwise a plain grep/sed fallback) that prints the assistant text, tool calls (`> Bash ls -la`), a `== turn done: N turns, X s` line after every finished turn (the CLI can keep running after a turn, e.g. waiting for background tasks) and, when the process really exits, a final `== exit <code>, total <s> s` line, and the CLI's own exit code is kept; `codex exec` already prints its progress. Without status tracking the tab falls back to the plain `-p` text mode. The tab keeps a normal shell afterwards so the output stays on screen. After each finished turn the formatter also logs `turn-done` in the tab log, and `turn-start` when the CLI writes again; while the CLI process lives on between the two (for example `claude -p` waiting for a background task), the tab shows *Watching · 12m* (blue dot) with the time since the last turn ended (*1h 15m* from an hour), and the tooltip gives when it ended with its day (*today 14:20*, *yesterday 23:40*). It goes back to *Running* when the CLI writes again. A successful exit shows *Idle* and its restart button starts another single pass; a failed run shows its exit code.

It means: one non-interactive session that ends by itself. You cannot answer or steer during the run, and tools that need approval are refused (no `--dangerously-*` flag is ever added). It applies only with the orchestra (the choice is one of the orchestra modes), and the install prompt always runs interactively.

Your alias for the CLI applies in Run once too (for example `alias agy='agy --dangerously-skip-permissions'`), so with such an alias nothing is denied. Without one, agy refuses every shell command without an allow-rule in `~/.gemini/antigravity-cli/settings.json` (`permissions.allow`, e.g. `command(git)`), ends the turn and still reports success. BoosterAI notices it: the formatter logs the denied command line, the tab shows *Denied: git, gh* (red, with a notification), and a bar in the main window offers **Allow and run again**. That adds `command(<program>)` for each program of the denied command line that is not allowed yet (on Windows in the WSL home), keeps everything else in the file and runs the affected tabs again. **Not now** hides the offer for those programs until BoosterAI restarts. `--mode auto` is no alternative: it needs agy's terminal sandbox. A rule allows the whole program, so `command(gh)` or `command(npm)` lets agy run anything those can do; review the list in `settings.json`. Detection needs python3 in the tab's Linux; `claude -p` denials are not detected yet.

It does not save tokens by itself: every turn sends the same context in both modes. In a test on #20 (claude haiku, a 34-line project) two identical one-shot runs differed more from each other than any mode difference could explain. How long each CLI waits for a background task after its turn ends was measured in #42 with a 62-minute background wait: `claude -p` stays alive and is re-invoked when the task finishes (62 minutes in the test); `codex exec` exits with status 0 as soon as the model ends its turn, because it has no tracked background tasks; `agy -p` waits at most 30 minutes (`waiting up to 30m0s for N background task(s)`), then ends the task and exits with status 0. BoosterAI never starts the CLI again by itself, whatever it could wait for.

**Idle watch with codex and agy.** An orchestra queue session that drains its queue keeps an idle watch (60 minutes in BoosterAI's own policy) and polls for new issues. `claude -p` keeps a background poll loop alive and wakes up when it finishes, so claude gets the plain command. For `codex exec` and `agy -p` such a loop would be dropped when the turn ends, so BoosterAI appends a host note to their orchestra command (`Launcher.ForegroundWatchNote`): `codex exec "$orkester (BoosterAI Run once host note: …)"` and `agy -p '/orkester (BoosterAI Run once host note: …)'`. It tells the session that the CLI exits with its turn and asks it to run every queue poll and the whole idle watch in the foreground of the turn, as blocking waits of at most 60 seconds (the core's interruptible waits), and to end the turn only when the session is finished. The CLI process then stays alive for the whole watch, the tab shows *Running* while it waits, and no second session is started. The cost is one short model call per wait (about 60 an hour with a cached context) instead of a sleeping background job. The note never goes into interactive tabs, the install prompt or claude. It is an instruction, not a guarantee: a model that ignores it still ends early, and the tab then shows *Idle* as before.

Verified in #49 with a stub queue project (an `orkester` skill over a local queue file, 60-second polls, a 3-minute idle watch) through the exact tab chain from `--dry-run` under `script`. `codex exec` (codex-cli 0.164.0) resolved the first item, polled every 60 seconds in the foreground, resolved an item added 75 seconds into the watch, moved the deadline, did a final poll and exited with status 0 after 5 minutes 45 seconds (16,596 tokens). The agy account had reached its quota during the test (agy 1.4.9 ended with `RESOURCE_EXHAUSTED`), so for agy only the mechanism is verified: a stub `agy` received the note intact as the `-p` argument, the tab logged `cli-exit` only after the stub's foreground waits, and claude's command is unchanged.

## Updates

With **Check for updates** on (the default, `"CheckForUpdates": true` in `config.json`), BoosterAI asks `https://api.github.com/repos/solwation/booster-ai/releases/latest` in the background at start, when the main window is activated and every five minutes while it stays active; an inactive or minimized window never checks. The last successful check is saved as `"LastUpdateCheck"`, and no check is made within five minutes of it, so at most 12 calls an hour stay well inside the 60 unauthenticated calls an hour that GitHub allows. Pre-releases and drafts are ignored, and the release tag is compared semantically with the app's own version (release builds get it from the tag, `-p:Version=${tag#v}`). The release body may hold `<!-- summary:sv: … -->` and `<!-- summary:en: … -->` markers (written by `tools/release-notes.sh` from `.github/release-summary.txt` at release time). The bar shows the one for the app language (the other when it is missing), stripped of tags and control characters and cut at 200 characters with an ellipsis, under *Version X is available*, with the full text as tooltip; *Show more* and the version in the bottom-left corner open **What's new** inside BoosterAI (#252): every release after the running version up to the new one, newest first, with the same content as the [release page](https://solwation.github.io/booster-ai/releases.html) (#245): with several releases an overview first, where features about the same topic are merged into one card with the latest screenshot and how-to, links to all their issues and the versions they span (#250); then each release with its summary, links to its cards and its list of changes, collapsed (open when only a few releases are shown). Each card has a screenshot, *How to use it* and links to the issue and the documentation, which open in the browser, as do the screenshots, *Release and downloads* and *Compare on GitHub*. The view is native, so it follows BoosterAI's language, light or dark theme, scaling and keyboard navigation (Tab between links, Esc closes; headings are announced as headings), and *Open in browser* opens the same range on the release page with the language and the resolved theme (`releases.html?from=<running>&to=<new>&lang=sv|en&theme=light|dark`; the page uses `theme` over the browser's `prefers-color-scheme` and keeps it when switching SV/EN and for *All releases*, #251). The data is `docs/releases.json`: the view shows the copy built into the app at once, then asks `https://solwation.github.io/booster-ai/releases.json` (8-second timeout) and redraws when it is newer; a successful answer is cached in `releases-cache/` next to `config.json`, and the cache is used offline when it is newer than the built-in copy. Offline the view says it shows the saved copy. Screenshots are not built in (to keep the package small): they are loaded from Pages, cached in the same folder, and shown as a short text when they cannot be had. An offered release that the data does not have yet is shown with its one-line summary from the update check. Without a newer release they open what is new in the running version, from the version it was updated from: each start records `"LastRunVersion"`, and a start of a newer version moves the previous one to `"UpdatedFromVersion"` (a downgrade clears it). An unknown version (a local `0.0.0` build) is left out of the range; the view and the page list every release without one, ignores an unreadable version with a notice and reads `docs/releases.json`, with the GitHub releases API as fallback for a release the file does not have yet. Older releases without markers show the bar as before. A network error or an unexpected answer shows nothing; the next minute tick or activation tries again.

When a newer release exists, a bar above the projects says *Version X is available* with three choices:

- **Update** downloads the archive for this platform (`BoosterAI-<version>-win-x64.zip` or `-linux-x64.tar.gz`) and `SHA256SUMS` from the release, refuses the archive unless its SHA-256 matches, and extracts only the executable, next to the installed one as `BoosterAI(.exe).new`. A small helper script then takes over and BoosterAI exits. On Windows it is a hidden PowerShell script (`%TEMP%\BoosterAI-update-<version>\update.ps1`, no window); it waits for BoosterAI to exit, moves the old exe aside, moves the new one in (and puts the old one back if that fails) and starts BoosterAI again. On Linux a detached bash script waits the same way and renames the new binary over the old one. The helper writes `updated` or `failed: …` to `update.log` next to `config.json`. Tabs already open keep running, but the new instance does not watch them; clicking *Update* is the confirmation.
- **Later** hides that version for a day (until the app restarts); a newer release shows at once.
- **Skip this version** saves it as `"SkippedVersion"` and does not offer it again; a later release is offered as usual.

Only a copy in the location the installers use updates itself: `%LOCALAPPDATA%\Programs\BoosterAI\BoosterAI.exe` on Windows, `~/.local/bin/BoosterAI` on Linux. Anything else (a development build, `dotnet run`, another folder, a non-x64 machine) shows the bar with **Open the releases page** instead, as does a failed update. The Linux self-update replaces only the binary; the menu entry and icons from `install-linux.sh` stay as they are. The checksum comes from the same release as the archive, so it protects against corrupt or truncated downloads, not against a compromised GitHub release.

## Local model hardware advice

Settings → **AI agents** → **Local models** opens a separate model manager, available even when no agent is installed. An agent is the program doing the work; an LLM is the model it uses, and Ollama is the server that stores and runs the local model. Several agents can use one server/model, but API connectivity does not guarantee reliable tool use or coding performance. The manager never changes agent configuration or selects a project tab's model.

The reviewed selection (2026-11-10) is a small, bundled catalog, not a complete or live model listing. Each entry links to its official exact-tag page and shows its rounded **total download size in decimal GB**, not a full RAM/VRAM requirement. Tags can be updated upstream:

| Exact Ollama tag | Approximate download | Role |
| --- | --- | --- |
| [`qwen2.5-coder:1.5b-instruct-q4_K_M`](https://ollama.com/library/qwen2.5-coder:1.5b-instruct-q4_K_M) | 0.986 GB | Small coding experiment |
| [`qwen3.5:4b-q4_K_M`](https://ollama.com/library/qwen3.5:4b-q4_K_M) | 3.3 GB | Text, code and tool-use example |
| [`qwen2.5-coder:7b-instruct-q4_K_M`](https://ollama.com/library/qwen2.5-coder:7b-instruct-q4_K_M) | 4.7 GB | Code generation and editing |
| [`qwen3.5:9b-q4_K_M`](https://ollama.com/library/qwen3.5:9b-q4_K_M) | 6.6 GB | Larger text/code/tool-use example |
| [`qwen3.6:35b-a3b-q4_K_M`](https://ollama.com/library/qwen3.6:35b-a3b-q4_K_M) | 24 GB | Family of the documented OpenHands local example |

The named starting suggestion uses a visible planning heuristic: download bytes × 1.25 + 2 GB. A GPU candidate needs that much **free VRAM on one measured GPU**, plus at least 2 GB free host RAM. Cards are never pooled. Otherwise enough free RAM makes it a CPU memory candidate. CPU suggestions prefer the small Qwen3.5 4B example, then the smallest fitting example, even on a high-RAM computer: spare RAM alone does not make a huge CPU model a sensible starting point. NVIDIA is the only measured GPU backend; unknown Intel/AMD hardware stays unknown. Missing RAM gives no named suggestion. This heuristic is not measured runtime memory, speed, coding quality or guaranteed context capacity; additional context, backend overhead and concurrent work can change the result. Measurements cover BoosterAI's OS, including the WSL allocation if BoosterAI itself runs there.

The separate manager reads hardware and the default loopback Ollama inventory when opened in the real app. Under the suggestion callout (the suggested exact tag and why), it works in three numbered steps: **1 Server** (address, **Check**, and a ✓/✗ result), **2 Choose model** (the catalog list; each row shows the tag, download size, planning fit and whether it is installed) and **3 Download**, which stays visible below the scrolling area. **Check** refreshes the specified server's metadata and any expired hardware reading. Confirm the server runs on the same OS, select an exact catalog tag and press **Download model** to explicitly call [`POST /api/pull`](https://docs.ollama.com/api/pull). Whenever **Download model** is inactive, the reason stands beside it (check the server first, already installed, confirm where the server runs, a check or download in progress). The target tag, size and server remain visible; inputs freeze while an operation runs. Every size in these windows and in the agent advice is in decimal GB. Pulls use streamed progress (percentages describe the current layer), 10-second response-header and 30-second inactivity deadlines, and a 16 KiB limit per status line. An explicit success message is required; HTTP failures, error records, malformed data and early EOF cannot report success. The installed-model list refreshes afterwards; a failed refresh is reported separately from successful download. Cloud metadata never counts as an installed local model. Existing models are never deleted.

Cancel or close stops this client's request/wait. Ollama may retain partial files for resume or continue a shared download; BoosterAI does not claim all server-side work stopped. No model is downloaded merely by opening the window, and missing Ollama leads to its [official installation page](https://ollama.com/download), not an automatic runtime install. Ollama owns the storage location; check disk space there.

After download, use the exact tag with the agent's documented local provider: [Aider](https://aider.chat/docs/llms/ollama.html) prefers `ollama_chat/<tag>`; [current Open Interpreter](https://www.openinterpreter.com/docs/terminal/models) selects a local provider with `--oss`; [OpenHands](https://docs.openhands.dev/openhands/usage/llms/local-llms) needs a compatible endpoint, substantial context (at least about 22k, preferably 32768) and reliable tools. Its Qwen3.6-35B-A3B hardware guidance is a recent GPU with at least 24 GB VRAM for quantized variants; the manager's variant-specific planning estimate is separate. Other entries have not been validated with every agent. Agent settings and reachable addresses still need checking: Windows, WSL and containers may have different servers and `localhost` refers to the caller's environment. Setup links are available in the manager.

Settings → **AI agents** shows local model advice on the Aider, Open Interpreter and OpenHands overview pages, **even before installation and without a project using that CLI**. The **All agents** cards link to it (*Local model: get advice →*) on installed agents; a missing agent's card offers **Install** instead. Install also remains on the agent's page. Advice applies to local inference, never to the CLI itself or its cloud/API use; it does not block installation or Start, change CLI configuration or download/load a model.

Opening AI agents automatically takes one lightweight hardware snapshot in the real app, shared by the three pages and cached for two minutes. Returning to the settings window or reopening the tab refreshes an expired snapshot; agent version checks use their separate 30-second cache. Constructors, tests and headless screenshots never start live hardware probes. Background installation/version updates preserve the advice, selected planning profile, navigation and unsaved editors. These agent advice pages do not contact a model server automatically. The separate **Local models** manager reads its loopback server inventory on opening or **Check**; only an explicit download action calls the pull endpoint.

No planning model is selected by default: the status explicitly remains **model dependent**, with measured resources and an explanation of how to proceed. You can install for cloud/API use, select a named planning example before downloading anything, or expand **Have a local Ollama model? Assess it** to check your actual installed model inline. There is no project-row advice link to discover first.

Planning examples have explicit assumptions and source links, verified 2026-11-09:

- Aider/Open Interpreter: `qwen2.5-coder:7b-instruct-q4_K_M` **on CPU**, using Ollama’s published **approximately 4.7 GB** [file-size estimate](https://ollama.com/library/qwen2.5-coder:7b-instruct-q4_K_M). Decimal GB are compared as 4,700,000,000 bytes; this is neither a locally measured file nor a full RAM requirement. Insufficient available RAM warns about this CPU scenario; room for the file does not establish context capacity, speed or coding quality.
- OpenHands: quantized **Qwen3.6-35B-A3B on one GPU**, using its documented [at least 24 GB VRAM guidance](https://docs.openhands.dev/openhands/usage/llms/local-llms). The published GB threshold is compared as 24,000,000,000 bytes, avoiding false rejection of nominal 24 GB cards whose reported MiB are slightly reserved. Multiple GPU capacities are not added together. Reaching the capacity level does not prove driver/runtime compatibility or speed; other variants, context sizes and multi-GPU setups need separate assessment.

Planning selections and measurements are temporary and do not change any tab or external CLI settings. New hardware snapshots recalculate planning advice and invalidate an old exact-model verdict; a late model-metadata response cannot restore a verdict based on the old snapshot.

A CLI name does not establish local inference. `ollama/` (also Aider’s `ollama_chat/`) identifies a provider, while the actual endpoint remains unknown. API-looking IDs are described as hints of remote inference and never receive a warning based on this computer’s resources. `standard`, Interpreter’s `local`, custom provider aliases and external configuration need explicit verification. Aider’s [`OLLAMA_API_BASE`](https://aider.chat/docs/llms/ollama.html), current Interpreter’s [`CODEX_OSS_BASE_URL`/port and saved provider](https://www.openinterpreter.com/docs/terminal/models), OpenHands’ [server configuration](https://docs.openhands.dev/openhands/usage/llms/local-llms), legacy CLI settings and shell wrappers can change the actual backend. BoosterAI does not try to reconstruct these overlapping settings.

In the inline Ollama assessment, enter the exact installed model ID and tag and confirm that the agent uses the specified loopback server **on the same operating system as BoosterAI**, outside WSL/containers. For a default/picker model, enter the actual ID after checking the CLI. This is an assessment input, not a model selection or endpoint override. Other local backends, LAN/remote endpoints, authenticated servers and unknown configurations retain an **insufficient information** result. You can still run them normally.

The check uses only read-only [`GET /api/tags`](https://docs.ollama.com/api/tags) and [`GET /api/ps`](https://docs.ollama.com/api/ps). It accepts loopback HTTP without credentials, proxies or redirects, with a four-second deadline and 1 MiB response limit for each request. It matches the exact tag (`:latest` only when omitted), and matches the loaded model’s name and digest. It never guesses bytes from “7B”, quantization labels or a different tag. Ollama’s remote-model metadata and cloud tags are treated as remote even when served by localhost: [Ollama can proxy cloud inference](https://docs.ollama.com/cloud).

Advice separates measured facts from estimates:

- RAM total/available and CPU identity/logical processor count describe the OS running BoosterAI. Windows uses `GlobalMemoryStatusEx`; Linux uses `/proc/meminfo` and `/proc/cpuinfo`. These do not establish WSL allocation, container/cgroup limits, CPU throughput or memory on a remote server.
- An optional `nvidia-smi` query reports each NVIDIA GPU’s total/free VRAM, with a three-second deadline, bounded output and process-tree cleanup. Missing tools, malformed readings and unsupported AMD/Intel devices leave GPU/VRAM **unknown**, never zero. Devices are not added together. [Driver/device support](https://docs.ollama.com/gpu) and the server’s actual GPU use remain separate questions.
- The installed model’s measured file size is only a rough lower comparison, not a complete runtime requirement. Quantization, [context, KV cache and concurrent requests](https://docs.ollama.com/faq) affect memory. An unloaded model whose file exceeds a measured GPU’s VRAM gets a conditional warning about CPU offload; other GPUs or a different backend can change that result.
- If you additionally confirm CPU-only server configuration, file size at least as large as total/available RAM produces a warning to choose a smaller model, close other programs or use remote inference. Without that confirmation, unknown GPU use cannot produce a CPU-only RAM verdict.
- A matching already loaded model supplies stronger evidence: Ollama’s reported CPU/GPU memory split explains likely slow CPU execution. A fully GPU-loaded model receives a qualified **memory capacity appears suitable for the current loaded configuration** result, without requiring its weights again in free host RAM. This is neither a speed benchmark nor a guarantee of coding quality, future context capacity or GPU compatibility.

No generic minimum RAM/VRAM threshold is assigned to an entire CLI. Missing model/runtime data stays explicit. All advice is temporary, advisory and based on the displayed snapshot.

## Setup: WSL and AI CLIs

BoosterAI checks what the tabs need when it starts, when its main window is activated and when Settings → AI agents opens. Activation and opening the page share a 30-second cache; checks never overlap. The WSL & environment page shows WSL installation facts from the automatic check and links to AI agents for program status, versions and settings. A quiet notice shows checking, unknown or failed status; a failed check keeps the last usable agent facts and does not reset navigation or unsaved selections. The check runs in the background with hidden processes, so no window opens and focus stays where it is, and the window stays usable meanwhile.

- **WSL (Windows only).** `wsl.exe -l -q` lists the distributions. Without `wsl.exe` or without any distribution a bar explains that BoosterAI runs the tabs in WSL and offers **Install WSL …**; a dialog first says that it needs administrator rights and usually a restart, then `powershell.exe -NoExit -Command "wsl.exe --install"` runs elevated (UAC prompt) in its own visible window. Afterwards: restart, open Ubuntu once to create the Linux user, then start BoosterAI again. When other distributions exist but not the one under *WSL* in Settings, the bar names them instead of offering an install. Everything else works as before while WSL is missing.
- **AI CLIs.** In the tabs' own login shell (`wsl.exe -d <distro> --exec bash -lic …` on Windows, `bash -lic …` on Linux), so PATH, nvm and aliases match a tab, BoosterAI runs `type -t` and `type -P` for `claude`, `codex`, `agy`, `aider`, `interpreter`, `openhands` and `npm`, with a 30-second limit after which the shell is stopped. A CLI counts as installed when an executable is on PATH; an alias alone does not count. Each missing CLI that a project row uses gets **Install &lt;cli&gt;** in a bar (all supported agents when none is installed at all, so a new user can start). *Not now* hides the bar until BoosterAI restarts.

The install runs in a new, visible tab through the same launcher as the orchestra's *Install* link, never silently: it prints what it runs, the installer's own output and questions, then either *done* with the next step (log in: `claude`, `codex login` or `agy`) or *the install did not finish*, and leaves a login shell (which already has the new PATH). A failure stays in that tab and BoosterAI keeps working. Nothing is installed before you press the button.

New tabs start a new login shell, so they find the CLI without restarting BoosterAI; *CLI not found* is a state of a tab that already ran, and its restart button runs the installed CLI.

### Agent versions and permission modes

Settings → **AI agents** opens an overview of all six supported programs. Each card has a 28 px logo plate with the theme-aware icon (Open Interpreter's mark is a filled disc, so it is not mistaken for a radio button), the name, exactly two lines, a status dot with **Ready**, **Missing** or **Needs update**, and **Permissions** (*Asks before tools* or *Approves automatically*, *Custom definition* for a definition BoosterAI did not write), and a last row: **Install** (a secondary button running the same install as the agent page) when the agent is missing, otherwise the link *Local model: get advice →* for Aider, Open Interpreter and OpenHands. The version, the alias name (*No alias*, *Auto Approve*, custom function) and *Not verified* are shown on the agent's own page, not on the card. Select a card or a sidebar entry to open an agent. If its executable is missing, the page shows its identity and **Install** button; Aider, Open Interpreter and OpenHands also show local model advice before installation. Installed agents provide **Overview**, **Permission alias** and **Context**, plus [**Accounts**](#accounts-per-agent) for Claude and Codex; their installation details and context calculations are collapsible, and the actual detected alias and selected preset preview stay visible. Each page scrolls independently; switching agents or sections keeps the same editors and unsaved selections. The same icons identify agents in the main window selectors. Choosing an alias asks for confirmation at once; the compaction **Save for model** action stays separate. Versions are program versions, not model versions. Detection runs in the background in the tab's login environment. Each executable's `--version` and `--help` probe is bounded to two seconds (plus 0.2 seconds to force termination), with bounded output; the overall check remains limited to 30 seconds. A failed version probe leaves an installed CLI marked installed with **Unknown** version. Help failure hides unverified presets. No model or account is contacted intentionally by BoosterAI.

An alias is a shell shortcut that expands a CLI name into a command with extra flags.
The permission page separates **Currently detected** (the actual shell alias or
function, or a direct CLI command) from the **Preview of selected option**. The
picker offers the installed CLI's supported presets and explains their effect.
**No alias** is the recommended starting point, not a guarantee of approval prompts:
external CLI configuration and organization policy still apply.

Custom aliases and shell functions have explicit labels rather than a generic
"Custom" permission level. Their definitions are shown as selectable text. Function
inspection uses `declare -f`, capped at 8 KiB, without executing the function; long
results carry a truncation notice. Choose a supported preset in the list
to replace a custom definition. One confirmation shows the detected definition and
the selected result, with the YOLO warning, the preview and its effect included when applicable. Cancel, Escape
and closing the confirmation leave the file unchanged and put the list back on the mode in effect; no manual shell commands are
required. Original definition lines and unrelated agents are preserved. A dedicated
per-agent override at the end of `.bashrc` clears the selected shell alias/function
and applies only the exact reviewed preset. No source filename is guessed.

**No alias** (internally `Standard`) clears the recognized alias; after an explicit
custom replacement it also clears that shell function. It does not reset the agent's
own configuration or organization policies. **Auto Approve** and **YOLO** are offered
only when the installed executable advertises the required flags. Selecting a value
writes nothing by itself: it opens the single confirmation, and only **Apply alias** there writes.
Approval and sandbox behavior differ by CLI:

| CLI | Auto Approve | YOLO | Official reference |
| --- | --- | --- | --- |
| Claude Code | `--permission-mode acceptEdits`: edits/common filesystem commands accepted; other tools may ask; sandbox unchanged | `--dangerously-skip-permissions`: permission prompts skipped, not an isolation layer | [Permissions](https://code.claude.com/docs/en/permissions) |
| Codex | `--approve-for-me`: automatic approval review with workspace-write sandbox | `--dangerously-bypass-approvals-and-sandbox`: approvals and CLI sandbox disabled | [CLI reference](https://developers.openai.com/codex/cli/reference/) |

**Codex's config.toml follows YOLO.** An alias only applies in interactive shells;
Codex started from a script, `exec`, tmux or as a subprocess reads `~/.codex/config.toml`
instead. Applying YOLO for Codex therefore also sets the top-level
`sandbox_mode = "danger-full-access"` and `approval_policy = "never"` in that file, after
the same confirmation. The first time, the file is copied to
`config.toml.before-boosterai-yolo` (an empty backup when it did not exist); applying YOLO
again keeps that backup. Choosing **No alias** or **Auto Approve** puts the two keys back
as the backup had them (removing a key it did not have) and deletes the backup; without a
backup the file is left alone. Only those two top-level lines change: tables such as
`[projects."…"]`, `model` and every other line stay byte-identical, and CRLF files keep
their line endings. The Codex permission page warns when the alias and `config.toml`
disagree (YOLO alias with a sandboxed config, which the warning's **Fix config.toml** button fixes after the same confirmation, or a
YOLO config under another mode). The same applies to the `CODEX_HOME` of every Codex
[account](#accounts-per-agent); the warning shows when any of them disagrees. A `CODEX_HOME`
set outside BoosterAI, profiles and project-level Codex config are not followed.

Normal preset edits retain support for older BoosterAI alias blocks. An explicitly
confirmed replacement uses a separate, canonical per-agent override; subsequent
changes edit only that override. Duplicate or malformed override blocks are refused
without writes. Other file bytes and other agents' overrides remain unchanged. This
affects regular terminals that read the same `.bashrc` too.

New tabs inherit the mode. Explicit starts/restarts in tabs opened with this version
refresh an explicitly confirmed override for that CLI, including clearing its old
function. Without such an override the older conservative ownership rule remains:
the original alias must have been proven and its shell value must remain unchanged.
The hook parses exact known rows; it never sources `.bashrc` again or evaluates file
text. Running CLI turns are unchanged. Tabs opened by older BoosterAI builds may
need closing and reopening. If another startup file subsequently changes the name,
detection continues to report the actual resulting alias/function. Install/update
buttons use the existing official installer path; the Interpreter standalone installer
does not migrate a legacy Python environment automatically.


## OpenHands CLI

`openhands` uses the [OpenHands CLI](https://github.com/OpenHands/OpenHands-CLI), not the GUI server. Settings detects its executable in the tab's login shell and offers the official standalone installer (`curl -fsSL https://install.openhands.dev/install.sh | sh`). Start it once to configure its provider and credentials.

Tabs run in the selected project directory. `standard` uses OpenHands' saved settings. A custom model is passed as `LLM_MODEL='<model>' openhands --override-with-envs`; this also enables OpenHands' other environment overrides (`LLM_API_KEY` and `LLM_BASE_URL`). Initial prompts use `--task`. Run once uses `--headless --task` and **OpenHands automatically approves actions in this mode**. Interactive tabs retain OpenHands' confirmation policy; the optional full-auto alias adds `--always-approve` only after the existing alias confirmation.

In-place restart starts a new conversation. OpenHands' `--resume --last` is global across projects, so BoosterAI does not select it automatically or offer Continue. Close all leaves a running OpenHands tab open with a manual-save message: save and exit in its terminal, or choose Force close. Exited tabs close normally. Output/status tracking and process-tree cleanup use the same tab lifecycle as the other agents. Automatic CLI updates are not enabled for OpenHands; update it using its installation method.

## AI CLI updates

With **Update AI CLIs automatically** on (the default, `"AutoUpdateClis": true` in `config.json`), a tab that starts claude, codex, agy or aider first runs `bs_update <cli>` from its `tab-lib.sh`, in the tab's own login shell (WSL on Windows, the local shell on Linux), so it uses the same PATH, nvm and installation as the CLI. An in-place restart (new model or AI, or restarting an exited CLI) runs it again before the new CLI; shell-only tabs, the *Install* link and a tab whose session library is unavailable skip it. `--dry-run` shows the `bs_update` step in each tab script and lists the commands below. The setting is read at each start and restart.

| CLI | Check and update |
| --- | --- |
| claude | `claude update`: its own check, also for npm or package-manager installs |
| codex | Installed with npm (the `codex` on PATH resolves under `npm root -g`): `npm view @openai/codex version` is compared with `codex --version`, and only a newer version is installed with `npm install -g @openai/codex@<latest>`. Otherwise (no npm, another installer) `codex update` |
| agy | `agy update`: the Antigravity CLI is a single self-updating binary (`~/.local/bin/agy`) with no package manager or check-only command, so its own updater decides |
| aider | `aider --upgrade`: its own self-updater directly from PyPI |

Each CLI is checked at most every six hours: the time is the stamp `~/.local/share/BoosterAI/cli-update/<cli>.checked` in the tab's Linux home (next to the CLIs it describes; on Windows the session folder is on `/mnt/c`, where file locks are unreliable). A tab that finds a recent stamp starts at once without any network call. The check holds `flock` on `<cli>.lock`, so tabs started together never run two installs of the same CLI: the others print *waiting for another tab's … update*, wait up to 45 seconds, find the fresh stamp and start the updated CLI (or skip after 45 seconds). The registry query is limited to 20 seconds and the update to 300 seconds. The tab prints one line, such as `BoosterAI: checking for a newer codex 0.165.0... updated to 0.166.0` or `... up to date`; when the check fails (offline, no write rights for `npm install -g`, missing `flock`/`timeout`, a timeout) it ends in `skipped: <reason>` and the installed version starts. The full output of the last update is kept in `<cli>.log` next to the stamp. A failed check is stamped too, so it is retried after six hours, not on every start; Ctrl+C stops a running update, starts the installed version and leaves the check due for the next start.

## Auto-clear when idle

Settings → **Memory and context → Context** groups the ways to keep an agent's context small: off, **Clear when idle** (this setting) or **Summarize** (auto-compact). Choose one mode; Off leaves each CLI's own defaults. Older configurations combining clearing and summarizing are preserved until you explicitly select a replacement. The page explains before the switch that auto-clear empties Claude's active context **without a summary**. It applies only to new or explicitly restarted Claude sessions. The summary-based alternative sits right below it on the same page; expandable details explain the idle guards.

With **Clear when idle** selected and its timer set to N minutes in Settings (`"AutoClearIdle": true` and `"AutoClearMinutes": 5` in `config.json`; off and 5 minutes when missing, 1 to 240 minutes), BoosterAI types `/clear` and Enter into an interactive claude tab once its claude has been idle for N minutes. Idle means all of:

- the last turn ended with nothing left running in the background: claude's `Stop` hook logged *idle*, not *waiting*, and no new prompt started since;
- the terminal has had no output for N minutes: the idle time counts from the later of the *idle* and the tab's last output (the time `script` last wrote `tabN.timing`), so any real activity starts it over;
- the tab's processes do not use the CPU ([CPU activity](#cpu-activity)): while the tab shows *Working* nothing is typed, and afterwards the N minutes count from the last poll at which it was still working.

`Stop` comes when claude's main turn ends, also while background agents, `run_in_background` commands, Monitor or a scheduled wakeup or `/loop` still run and will start the next turn themselves (#71). The hook input then lists them in `background_tasks` and `session_crons`; with any entry the hook logs *waiting* instead of *idle*, and the tab shows *Running*. The task notification or wakeup that follows starts a turn (*busy*) like a typed prompt, and the turn that ends with nothing left logs *idle*. The output check is a second guard: a running background agent redraws its timer about every second, so a claude too old to list its background work is not cleared either. An idle claude writes nothing to the terminal. A background command or a pending wakeup can be silent for minutes, which is why the hook's list is needed. When in doubt it does not clear: without an output record (`tabN.timing`) it never does, and a status line that keeps redrawing or a key pressed in the tab postpones it. It does so once per idle period; the next prompt (*busy*) starts the next period. Claude's `/clear` starts a new session with an empty context and keeps the previous one on disk (`/resume`). The status then reads *Idle · cleared HH:mm* until the next turn, and its tip says what happened.

It never types into a tab that works on a turn, whose CLI has exited or whose tab has closed, a Run once tab (`bs_stream`, `claude -p`, which also shows *Watching*), a tab waiting for *Restart when idle*, or a tab that *Close all* is closing. It also skips the period when a key was pressed in the tab after that turn's prompt was sent (a draft or an answer to a permission prompt in the input box would otherwise be sent along with `/clear`; see [what counts as a key](#what-counts-as-a-key)).

| CLI | Auto-clear |
| --- | --- |
| claude | Supported: hooks report when a turn ends; `/clear` starts no turn |
| codex | Skipped: no hooks, so BoosterAI only knows that its output has been quiet, which a long tool call also is; typing could land in the middle of a turn |
| agy | Skipped, for the same reason |
| Shell | Skipped |

How it works: a terminal gives no other program a way to type into a running CLI (`TIOCSTI` is disabled on current kernels), so with the setting on, a claude tab runs its CLI under `bs_pty` from `tab-lib.sh` (`bs_run '…' input` in the tab script, visible in `--dry-run`). `bs_pty` is a small `python3` relay between the tab's terminal and the `script` that records the output: it gives `script` a pseudo-terminal of its own with the tab's settings and size, passes every byte through unchanged both ways (keys, paste, mouse and focus reports, raw mode, colours) and copies window size changes. Once a second it looks for `tabN.input` in the session folder, which BoosterAI writes atomically: the time the turn started and the text. It deletes the file, types the text and, 0.3 seconds later, the Enter on its own, so claude sees a typed command and not a paste, and logs `input-sent`; or, if a key was pressed after that time, only `input-skipped reason=typed`. Its own waits (the Enter, the once-a-second look, how long output has been quiet, a request at most 10 seconds old, the half second an unfinished terminal reply may take) are timed on the monotonic clock, so a step of the wall clock, which WSL makes by seconds on some machines, neither splits a reply into a key nor types into running output (#280); only times in the log, which other processes compare, use the wall clock. It logs `input-ready` when it starts, and BoosterAI only asks tabs whose CLI logged it. Nothing opens a window or takes focus, on Windows (the request is a file on `/mnt/c`) or Linux. Stopping the CLI (an in-place restart or *Close all*) reaches it through `bs_pty` as before; when the terminal closes, `bs_pty` stops `script` and the CLI instead of leaving them behind.

The setting is read when a tab starts or restarts in place: turn it on, then start or restart the claude tabs it should apply to. A tab without `python3` in its Linux, started with the setting off, or started by an older BoosterAI runs without `bs_pty` and is never cleared. The idle time is measured from the *idle* time in the tab's log (WSL's clock on Windows), so a WSL clock that has drifted from Windows shifts it by the same amount. After an auto-clear, *Continue* and *Close all* continue the latest conversation in the directory as claude chooses it (`claude --continue`), which may be the new, cleared session rather than the one before `/clear`; use `/resume` in the tab to pick the earlier one.

### What counts as a key

Everything the tab's terminal sends reaches the CLI unchanged and at once; `bs_pty` only looks at a copy to decide whether someone typed. Replies the terminal sends on its own are not keys: answers to the CLI's queries (device attributes, mode reports `DECRPM`, the kitty keyboard reply, `XTVERSION` and other DCS/OSC/APC strings such as colour replies, the cursor position report), colour-scheme and in-band size reports, focus reports, and SGR mouse reports for movement and the wheel. Keys, paste (bracketed or not) and mouse clicks are; so is anything not recognized, and a report mixed into the same read as a key does not hide the key. A cursor report from row 1 looks like a modified F1–F4 and counts as a key. A sequence split across two reads is classified once it is complete; one that stays unfinished for half a second (a lone Escape key) counts as a key, and a request arriving while one is pending is skipped. The log gets `input-typed` at most once a second, with the time of the latest key, so mouse movement or a long paste does not grow it; the skip decision itself uses every key's exact time. When in doubt it counts as typed: a skipped `/clear` or reload is harmless, a draft sent along is not.

## Watching the tabs

After an app restart or update, BoosterAI recovers both live tabs and previously
started closed/lost tabs from retained session metadata. **Restart all** includes
ended ordinary tabs and orchestra tabs together. Live shells take precedence over
closed history; recovery never opens a terminal automatically. Tabs that were never
started, or whose session metadata has been cleaned up, are not marked restartable.

After **Start**, BoosterAI stays running and shows a status per tab: *Starting…*, *Running*, *Working* (a process in the tab uses the CPU while the agent is idle, see [CPU activity](#cpu-activity)), *Watching* (Run once only: a turn ended and the CLI waits), *Exited · error (code)* (a non-zero exit), *CLI not found*, *Did not start*, *Tab closed* or *Lost*. What the window does after Start is the *After Start* setting (`"AfterLaunch"` in `config.json`): `keep` (the default) leaves it open, `minimize` minimizes it, `close` closes BoosterAI. An old `"CloseAfterLaunch": true` without `"AfterLaunch"` reads as `close`. On Windows the tray icon is shown after Start in the keep and minimize cases; with *Close and minimize to the system tray* on, minimizing hides the window there (Windows may tuck the icon behind the ^ arrow): the close button (X, Alt+F4) and Minimize hide it from the taskbar instead of quitting, and a click on the icon or *Show BoosterAI* brings it back; *Quit* in the icon's menu really quits, as does an update install. This is the *Close and minimize to the system tray* setting (`"MinimizeToTray"` in `config.json`, on by default); with it off, or if the tray icon cannot be shown, Minimize leaves a taskbar button and closing the window quits BoosterAI. Choosing *Close* after Start closes the app regardless. Linux gets no tray icon and keeps that taskbar behaviour, because many desktops (plain GNOME, for example) have no tray. A tab that has closed or whose CLI has exited gets a restart button. The button starts the same AI, model and orchestra choice. If the CLI exited while the tracked shell remains alive, it queues `RestartScript` through `QueueNext` and runs it in that same tab, preserving the title, track and log. The next `cli-start` changes the status back to Running. This also applies to Continue and Run once, regardless of selections edited since launch. PID and `/proc` start time must match; a closed or reused PID is never treated as a live shell. Tabs opened by older builds without the idle-shell restart capability use the closed-tab fallback.

For a closed or lost tab, Windows keeps `wt -w <session> new-tab`. Linux deliberately opens a new window: Ptyxis `--tab` and gnome-terminal/xfce4-terminal `--tab` select an active/last window, and BoosterAI has no verified target for the session's window. Konsole's `--new-tab` also lacks a verified session target, so each call uses `--separate`. Kitty, wezterm and xterm likewise keep their new-window behavior. This prevents a restart from entering an unrelated terminal window. A batch of closed tabs restarted together shares one fresh window in Ptyxis, gnome-terminal and xfce4-terminal; Konsole and the other terminals use separate windows. If the session window is gone, the same fallback applies. `--dry-run` prints the explicit join-request fallback for every terminal.

**Start one tab.** A tab this BoosterAI run has not opened yet, such as a subtab created while the others already run, has a start icon (a triangle) in the status column where ↻ sits, and **Start** in its row menu (#198). It opens only that tab, ticked or not, and leaves its tick as it is: no other ticked tab starts and open tabs are not touched. It uses the same path as reopening a closed tab, so the tab joins the terminal window of the running session; before any session it opens a new window, exactly like **Start** with only that tab ticked, and later starts join that window. Once the tab has been opened it gets ↻ (and **Continue** where possible) instead, so the two never show together. Its accessible name says which tab it starts (*Start Atlas-docs*) and its tooltip that no other tabs start. A new subtab inherits its project's tick, so the main **Start N tabs** button counts it as before; the start icon is the way to open just that one.

**Continue an ended conversation.** Beside the regular restart button (↻), the word **Continue** reopens an ended or closed interactive AI tab with its original choices and the latest conversation in its directory: `claude --continue`, `codex resume --last` or `agy --continue` (supported by the installed agy CLI's `--help`). It sends no initial prompt, including `/orkester`. The tooltip and status say that the conversation is continued. This is explicit each time; regular restart and **Start** still start fresh. It is shown only when continuing is possible; its accessible name says which tab's conversation it continues. Plain shells and **Run once** tabs have no **Continue**: Run once's restart deliberately starts another orchestra pass. The CLI chooses the latest conversation, not a per-tab conversation ID; tabs sharing a directory can therefore continue each other's conversation. Use separate directories when their histories must stay separate. If the continued start does not get going (the CLI exits with code 1–127 within 15 seconds, as Claude does with no saved conversation), the tab falls back once to a normal fresh start with the same agent, model and settings, including `/orkester` when the tab has the orchestra on; this applies to **Continue**, **Restart all**, an in-place restart with conversation and a model change that continues. A session that ran longer, a quit with code 0 or an exit by signal is never relaunched (#235).

**Changing the agent or model of a running tab** shows the restart button too, with the status *Running – new choice* and the tip *Restart the tab with &lt;agent&gt; / &lt;model&gt;*. The restart happens in the same tab: BoosterAI queues the new command in the session directory (`tabN.next`), then stops the tab's foreground process group, which is the CLI and never the shell. The tab's chain then runs `bs_next` from `tab-lib.sh`, which starts the queued CLI and logs it like the first one. After a CLI exits, `bs_shell` retains that chain around the ordinary interactive shell. It records the idle child shell's PID and start time; a queued restart wakes only that child with HUP (interactive bash ignores TERM), repeated until the child is gone because bash misses a HUP that arrives while its prompt is still starting (#122), then the original parent consumes `bs_next` again. A delayed wake cannot signal a new CLI that already consumed the queue. The idle child sources `~/.bashrc` before it records itself, which can take seconds; a restart queued meanwhile is not lost: right after recording itself the child checks for a queued command and hands it to the parent at once, and the wake waits up to 30 seconds for tabs started by older builds. If no idle shell appears in that time, BoosterAI takes the queued command back (so it never runs later by surprise) and says in the status line that the restart did not get through. Each restart starts exactly one CLI. Exiting the idle shell normally still closes the tab. A model change on `claude` or `codex` keeps the conversation (`claude --continue --model X`, `codex resume --last --model X`). A new agent, agy or a Run once tab starts fresh. Changing back to the running choice removes the button.

**Clean terminal before every CLI start (#67).** A TUI that was stopped or has exited can leave the alternate screen, mouse reporting, bracketed paste, a hidden cursor or odd attributes behind, and the next CLI then draws wrongly (previously: `exit`, `clear`, start again). `tab-lib.sh`'s `bs_reset` therefore runs right before `bs_cli` in the tab chain, in the queued `RestartScript` (restart in the same shell, in WSL as on Linux) and in a reopened closed tab's script: `stty sane`, leave the alternate screen, mouse modes off, bracketed paste off, cursor shown, DECSTR soft reset, attributes reset, then clear screen and scrollback. It is deliberately a soft reset, not `ESC c`, so the tab title stays. It only writes when stdout is a terminal and never fails the chain.

**No recaps in Claude tabs (#241).** Every Claude command BoosterAI starts (start, continue, restart, Run once, save-and-close, any model) is prefixed with `CLAUDE_CODE_ENABLE_AWAY_SUMMARY=0`. Claude Code otherwise writes an away summary (*recap*) when a session that sat idle gets focus again, and each one is an extra model call; BoosterAI tabs are often idle for long stretches. The variable applies only to that CLI process (shell aliases included) and wins over `awaySummaryEnabled` in your own Claude settings, which BoosterAI does not change. Codex writes automatic recaps as well; its commands get `-c tui.auto_recap=false`, a per-run override that leaves `~/.codex/config.toml` unchanged. Antigravity (agy), Aider, OpenHands and Open Interpreter have no such automatic summary in the versions checked.

**Splash in every tab (#242, #244).** After the terminal reset of every interactive start, continue and in-place restart, `tab-lib.sh`'s `bs_logo` shows BoosterAI's mark and wordmark in half-block pixel art as a splash in the middle of the tab, horizontally and vertically, on the terminal's alternate screen: a gradient sweep (about half a second), a short hold, then a fade towards the dark background, after which the alternate screen is left and the CLI starts at the top of the clean screen with nothing of the splash in the scrollback. It takes about 1.2 s; frames are dropped after 0.8 s (sweep) and 1.5 s (all). Windows Terminal (`WT_SESSION`) and terminals with `COLORTERM=truecolor` get 24-bit colour, others with 256 colours the palette; `NO_COLOR` or fewer colours show a still, plain, centred logo for 0.6 s and clear it (via `tput`). It picks the largest variant that fits (mark and wordmark from 80×16, wordmark from 60×10, one coloured line from 12 columns, nothing narrower), hides the cursor meanwhile and always restores the screen and cursor, also when interrupted. Run once, untracked scripts, non-terminal output and `TERM=dumb` skip it, and the resume fallback's fresh start does not repeat it. Turn it off under **Settings → Utseende → Visa animerad BoosterAI-logotyp i flikarna** (`ShowTabLogo`, on by default).

**Tab names (#66).** Each tab is named after its entry in BoosterAI and keeps that name. The terminal gets it on its command line (Windows Terminal `--title`, without `--suppressApplicationTitle` since #281 because that also blocks the new title after a rename, Ptyxis `-T`, which also makes Ptyxis ignore titles set by programs, konsole `tabtitle`, kitty `--title`, xterm-style `-T`, gnome-terminal and xfce4-terminal `--title`, where current gnome-terminal versions ignore it; wezterm has no option). The tab script repeats it: `tab-lib.sh` gets the name as its third argument, keeps it in the session's `tabN.title` (which BoosterAI rewrites when the tab is renamed, #281) and `bs_title` sets the name from that file with an OSC 0 title sequence whenever a CLI starts or exits, and the idle shell's prompt adds the same sequence after `~/.bashrc` (the name literally, without control characters), so a title set by the CLI or the shell's own prompt is replaced at the latest at the next start, exit or prompt. Claude Code is told not to set titles (`CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` unless you set it yourself; this also stops its other tab status writes). Codex and agy can still set a title while they run where the terminal accepts it (not in Ptyxis with `-T`), until the next status poll restores the name. Ptyxis also appends the foreground program's command line to a tab name unless that program is a shell, which made the tabs read `name — script --quiet …`; `bs_run` and `bs_stream` therefore run the CLI below a bash subshell (`bs_fg`), which stays in the foreground group and waits for the CLI when BoosterAI stops it. When the tab's terminal hangs up (its window or tab is closed), `bs_fg` stops that foreground group with TERM within about a second, so `script`, which ignores the hangup, and the CLI under it end with the tab instead of staying behind, also without `bs_pty` (#70). BoosterAI cannot read a tab's current title back from the terminal, so it re-applies the name rather than detecting a change.

The status shows *Running* while terminal output is arriving and *Idle* after 60 seconds without output. Successful CLI exits also show *Idle* while the shell remains open; failures and closed tabs keep their separate states. Tabs started before output timing was available show *Activity unknown* until they are restarted. Interactive `claude` tabs additionally use `--settings tabN.claude.json` hooks to report when a prompt starts and a turn ends. The `Notification` hook is not used, because it also fires for a permission prompt in the middle of a turn. A turn that ends while background work still runs logs *waiting* and counts as working (see [Auto-clear when idle](#auto-clear-when-idle)). If the CLI is working, the restart asks first: **Restart now** interrupts the turn, and **Restart when idle** makes the row wait (*Waiting for idle…*, a second click cancels) until the next *idle*. An idle `claude` restarts without asking.

**Tabs that already run.** Each started tab saves its choices next to its log (`tabN.tab.json`). When BoosterAI starts, for example after an update, it looks through the session directories for tabs whose shell is still alive (same PID and start time in `/proc`, no *exit* in the log). Each one is matched to the configured tab with the same persistent ID (legacy metadata uses the main tab's name and directory) and is watched again, with status, restart and in-place restart, and the status line briefly says how many running tabs were found. That startup notice disappears when the first recovered tab changes state (for example its CLI exits or the tab closes), a new launch or restart starts, or another status replaces it. A delayed recovery lookup never overwrites a newer status. A recovered claude tab keeps auto-clear when it was started with it (its log says so). If the choice has changed since that tab was started, it shows *Running – new choice*. **Start** opens only the chosen tabs that are not running: the button counts those, says *All chosen tabs are running* when there are none, and opens new tabs in the window of the newest session it found. A session older than two days is kept while one of its tabs still runs.

When something unexpected happens (a tab closes, does not start, or its CLI exits with an error), BoosterAI shows a system notification. On Windows this is a toast. On Linux it uses `notify-send` when that is installed. Clicking the notification brings the BoosterAI window back, also from the tray (on Linux this needs a `notify-send` with `--action`, libnotify 0.7.9 or later). In *Settings* you can turn **Notifications** off, and you can set **After Start** to *Close* to get the old behaviour back.

**Sound effects (#240).** *Settings → General → Sound effects* (`SoundEffects` in `config.json`, on by default) plays a short, quiet chime for four events: a tab that ended unexpectedly or is waiting (the same event as the notification above), a tab that failed to start (the error notification), low quota and quota back (#239). Each has its own sound (`finished`, `error`, `quota-low`, `quota-back`) and the same sound plays at most once per 4 seconds. Sounds and notifications are independent: *Notifications* off silences the toasts only (including the quota toasts; the in-app quota bar is unaffected), *Sound effects* off silences the sounds only. The WAV files are embedded in the app; on Windows they play through winmm `PlaySound` from memory, on Linux through `paplay` or `aplay` when on PATH (otherwise silent). `BoosterAI --play-sound <name>` plays one and exits. `MainViewModel.Sound` is silent unless the app installs the real player, so tests and `--screenshot` make no sound.

How it works: each Start creates a session folder (`%LOCALAPPDATA%\BoosterAI\sessions\…` on Windows, which WSL writes to through `/mnt/c`, or `~/.local/share/BoosterAI/sessions/…` on Linux) containing a small `tab-lib.sh`. Each tab's shell sources that script, and it appends `start` (PID and start time), `cli-start`, `cli-exit rc=N` and `exit` to the tab's log. Interactive commands run through `script`, which records their output timing (the activity). The wrapper keeps `~/.bashrc` aliases and shell functions available. If the library cannot be loaded, the CLI (including Run once) or plain shell still starts in its project directory without tracking or status hooks, and leaves a normal shell afterwards. Aliases, arguments and explicit continuation are kept; Run once uses plain CLI output instead of the stream formatter. No status log is fabricated, so BoosterAI cannot monitor or restart that fallback shell in place. The app polls the logs every 2 seconds. A shell that is gone without logging `exit` (for example after `wsl --shutdown`) counts as *Lost*. Windows detects this through `\\wsl.localhost\<distro>\proc`. Session folders older than two days are removed.

**Compact status column.** The **Status** column is narrow and fixed (160 px, #209); the project column takes all the free width. Each row shows its status as a coloured dot, followed by the remaining plan share on a live tab with a known limit (*38%*, see [Accounts](#accounts-per-agent)), *!* on an error row (the CLI exited with an error, is missing, the tab did not start, was denied or lost) so colour is never the only cue, or *…* while the tab closes or waits for idle to restart; other rows show only the dot. The row actions follow at the column's right edge: ↻, *Continue* or the start triangle. The full status text is in the popup below and in the dot's accessible name.

**Status popup.** Hovering a tab's status dot, or focusing it with Tab and pressing Enter/Space, opens a compact popup (430 px wide, readable in light and dark) with the tab's name, agent and status, the longer explanation when the status tip says more than the status itself (for example what *Watching* means), the account's plan limits table (#200, #210) and, for a live AGY tab without limits, why they are missing (#212). After a CLI exit with an error, a click or Enter opens it with *Restart* (↻) as its primary action. It shows no terminal text and BoosterAI neither captures nor reads a tab's output for it (#216). Keyboard-opened details stay open and scroll at small window sizes; Escape closes them and restores focus to the status control. Activating this control never starts a tab. Nothing is refreshed while the popup is open: it shows the state when it opened.

The only output-related file BoosterAI reads is `tabN.timing`, which util-linux `script` touches on every write (`--log-timing`; the output itself is not logged): the activity fallback ("Running" while output arrives, "Idle" after 60 seconds), auto-clear's output check (#71) and the orchestra reload's quiet check use its modification time. Nothing reads the last lines, so neither the closing/save flow nor the "CLI exited" error display depends on them; the exit code comes from the log (`cli-exit rc=N`).

Known limit: when you close a Windows Terminal window that holds several tabs, WSL may keep their shells alive for up to about a minute, so *Tab closed* can appear late.

`--screenshot` shows sample statuses and renders the window headless, so nothing appears on screen (see [Development](DEVELOPMENT.md#screenshots)).

**Restarting many tabs.** From two restartable tabs a *Restart all (N)* button appears left of *Start* (disabled while Close all runs). It applies each tab's own restart rules: ended or unchanged tabs and changed tabs with an idle CLI restart at once (closed tabs among them reopen together, in one new window where the terminal allows it), a changed tab already waiting for idle stays queued. Changed tabs whose CLI is working on a turn are never interrupted silently: one combined question (*Restart now* / *Restart when idle* / *Cancel*) covers all of them, and Cancel cancels the whole action. Waiting for idle is only offered when every such tab can be detected as busy (not Run once tabs or tabs of unknown activity).

**Ending the day.** **Close all** asks first, then interrupts each running AI's current turn and continues its latest conversation in the project directory with a request to save, commit and push completed work and stop. It uses `claude --continue -p`, `codex exec resume --last` or `agy --continue -p`; it sends no new orchestra prompt and adds no permission bypass. Live interactive CLIs get the instruction even when their output is idle: output silence cannot establish that they have no unsaved work. Shell-only tabs, exited CLIs and Run once tabs already Watching close immediately. A separate token in the tab log identifies the save turn, so an earlier turn ending cannot close the tab prematurely. The progress dialog shows each tab saving or closed, offers **Force close** throughout, and highlights a 10-minute timeout. A failed/denied save leaves its terminal open for inspection. If you save and exit that terminal manually, the dialog recognizes its logged shell exit without retrying the save or sending further commands. Missing or unreadable process data alone does not prove closure: without a logged exit or a verified reused PID, the error remains for manual inspection, Cancel or explicit Force close. **Cancel** stops further automatic closing; save turns already started may finish, and closed tabs stay closed.

Continuing selects the latest conversation per AI and directory, so two watched tabs sharing both are left open with an explanation instead of choosing a conversation implicitly. Directory aliases such as symlinks and sessions opened outside BoosterAI can still make “latest” ambiguous: save those manually. Force close stops each recorded shell's foreground process group and descendants, checking `/proc` start times before signals to avoid reused PIDs. A supported shell first gets USR1 to return success; legacy or surviving shells get HUP and then KILL after a short grace period. It never kills a shared terminal server or unrelated window. Newly opened tab shells advertise a USR1 close handler (and handle HUP as a normal close) and return exit code 0 after their foreground children are stopped, so normal terminal exit handling can close them. Windows tabs always select the private BoosterAI profile with `closeOnExit: "always"`, including at default zoom, to close even after forced termination; the last such tab closes its window. Older tabs already open before this support, manually added tabs, Linux keep-open preferences and real Windows Terminal window closure have not been verified here: the full window-closing acceptance remains open until checked on Windows. No window is closed by a guessed title or a shared terminal-server PID. Tabs from older versions without a verifiable shell remain open for manual handling. Saving and pushing are requests to the CLI: denied tools or its own report may still require manual action.

### Tab status channel

The tabs' agents can report what they are doing and ask the user questions through plain files in the session folder (#246, #247): no network port, no socket, nothing leaves the computer, and it works the same with Windows Terminal + WSL (`/mnt/c`) and on Linux. *Settings → General → Let the agents in tabs report status and questions to BoosterAI* (`TabStatusChannel` in `config.json`, on by default) controls it; it is read when a tab starts or restarts, and when it is off no tab exports or registers anything of the channel: tab scripts are exactly as without it. Below are the file protocol and BoosterAI's reader, then the agent's side (#248) and the display in the main window (#249).

**Format version 1.** Every line and answer carries `"v":1`; a reader ignores lines without it or with a higher version.

- `tabN.events`: JSON Lines, append-only, written by the agent's side; each line is one JSON object ending in `\n`, with `at` (epoch milliseconds from the tab's clock, the same clock as the tab log) and `kind`:
  - `{"v":1,"at":1793007090000,"kind":"status","state":"done","text":"Finished, nothing left to do"}`, where `state` is `idle`, `working`, `blocked` or `done`. The latest one counts.
  - `{"v":1,"at":1793007091000,"kind":"question","id":"q1","text":"Which branch?","options":["main","dev"],"free":false}`. `id` is 1–64 characters of letters, digits, `-`, `_` and `.` (not first), because it is a file name; `options` may be empty; `free` allows a free-text answer and defaults to true without options. A question without options that does not allow free text is ignored, and asking again under the same id replaces the earlier question. An optional `expires_at` (epoch milliseconds, after `at`) says when the asker stops waiting; after it the question is shown as stale (#249).
- `tabN.answers/<id>`: BoosterAI's answer, a single JSON object: `{"v":1,"id":"q1","question_at":1793007091000,"text":"dev","at":1793007095000}`. `question_at` is the `at` of the question it answers, so an answer left from a question that used the same id earlier (for example before an in-place restart) does not count for the new one. The agent's side waits for the file to appear and reads it whole; it never sees half an answer.
- `tabN.notice`: a note from BoosterAI to the agent (#275), a single JSON object `{"v":1,"id":"quota-session-1795799970218","text":"…","at":1795799970218}` written to a temporary file and renamed, so a newer note replaces one not yet taken. The agent's side finds it beside the events file (the events path with `.notice` for `.events`), takes it by renaming it away (so it is delivered once), adds the text to the current tool result after *Message from BoosterAI (the app that runs this tab, not the user):* and appends `{"v":1,"at":…,"kind":"notice-read","id":"…"}` to `tabN.events`.
- The agent's side finds them through `BOOSTERAI_TAB_EVENTS` (the events file), `BOOSTERAI_TAB_ANSWERS` (the answers folder) and `BOOSTERAI_TAB_PROTOCOL` (`1`), as the tab's shell sees the paths. They are exported only into tabs started with the setting on (see *Agent side* below), and `--dry-run` prints them.

**Reading.** BoosterAI reads the events since the latest `cli-start` in the tab log: events from a CLI that an in-place restart replaced do not count. A question is open until an answer with its id and `question_at` exists. The reader tolerates the agent writing at the same time (the file is opened shared and a last line without its `\n` is still being written and skipped), broken lines (invalid JSON, unknown kinds or states, missing fields, unsafe ids are skipped one by one) and oversized files: only the last 1 MiB is read, from its first whole line, and texts are capped (2,000 characters, at most 20 options of 200).

**Answering.** An answer is accepted once per question: the writer first creates `tabN.answers/.<id>.lock` exclusively, checks that no answer for that question exists, writes a temporary file beside it and renames it to `<id>`, then removes the lock. A second answer, also one sent at the same time from another BoosterAI window, is rejected; so is an answer to a question that is not open, an empty one, one longer than 4,000 characters or, without `free`, one that is not among the options. A lock left by a writer that died is taken over after 10 seconds.

**Agent side (#248).** Every session folder holds `bin/boosterai-tab`, one python3 script that is both the fallback command and a stdio MCP server, and `boosterai-mcp.json`, Claude Code's MCP configuration for it. They are inert: only a tab started (or restarted in place) with the setting on uses them. Such a tab's script first runs `BOOSTERAI_TAB_EVENTS=… BOOSTERAI_TAB_ANSWERS=… BOOSTERAI_TAB_PROTOCOL='1' PATH='<session>/bin':${PATH#'<session>/bin':} && export …` (no `;`, no `"`, and `bin` is never added twice), so the variables and the command reach the CLI and the shell left after it.

- **Tools.** `boosterai_status(state, text)` appends a status event and returns at once. `boosterai_ask(question, options[], allow_free_text, timeout_seconds)` appends a question with a new id (`q<hex ms><4 random>`) and `expires_at` (its `at` plus the timeout) and waits for `tabN.answers/<id>` with the question's `at` as `question_at`, polling twice a second; it returns *The user answered: …*, or after 15 minutes by default (1 s to 60 min) *No answer from the user within …* as a normal result, so the agent goes on. BoosterAI then shows the question as stale. `allow_free_text` defaults to true without options and false with them; texts are trimmed to the reader's limits. The server answers `initialize` (protocol 2024-11-05 to 2025-11-25), `ping`, `tools/list` and `tools/call`, runs each ask in its own thread so other requests are still answered, and stops waiting on `notifications/cancelled`.
- **Command.** `boosterai-tab status idle|working|blocked|done [text]` and `boosterai-tab ask [--option TEXT]… [--free|--no-free] [--timeout S] QUESTION`, which prints the answer (exit 0), or the no-answer message on stderr (exit 2); exit 1 outside a tab with the channel on.
- **Why python3.** The server must parse JSON-RPC reliably, which bash cannot without a new dependency (jq), and the BoosterAI binary is a Windows program on Windows, out of reach of a WSL tab without interop and path translation. python3 is already what the tab's Linux needs for `bs_pty` and the status lines. Without it the server does not start (the CLI starts as usual and shows the server as failed) and the command fails; nothing else changes.
- **Claude Code** (interactive starts, continuations, the install prompt and in-place restarts; never Run once or Save and close): `--mcp-config <session>/boosterai-mcp.json --allowedTools mcp__boosterai --append-system-prompt '<instruction>'`, last on the command line so that no option that takes several values swallows the prompt. `--mcp-config` adds the server to the user's own (no `--strict-mcp-config`), the user's settings files stay as they are, and the allow rule only lets the two tools run without a permission prompt. The server inherits the variables from claude.
- **Codex** (the same starts): `-c mcp_servers.boosterai.command=python3`, `args=['-I','<session>/bin/boosterai-tab','mcp']`, `env_vars=[the three variables]` (Codex passes only a few variables to MCP servers), `tool_timeout_sec=3660` (its default of 60 s would cut an ask short), `default_tools_approval_mode=approve` and `-c developer_instructions=<instruction>`; `~/.codex/config.toml` is not changed, but a top-level `developer_instructions` of the user's own is replaced for that tab. A session path with `'` gets no server.
- **Other agents** (agy, aider, openhands, interpreter): the variables and the command only. agy keeps MCP servers only in its global `~/.gemini/config/mcp_config.json`, and none of them has a per-run instruction option, so they are not told about it.
- **Instruction** (48 words): *You run in a BoosterAI tab. Call boosterai_status with state done when you have finished and have nothing left to do, blocked with the reason when you cannot continue, and working when you start a new task. Use boosterai_ask only for questions that only the user can answer.*

**In the main window (#249).** BoosterAI reads each started tab's channel at every 2-second status poll, only while the setting is on; turning it off hides everything below at once.

- **Status line.** While the tab's CLI runs, the agent's latest status is a line under the row: a green check for *Done* (*Klar*), an amber warning for *Blocked* (*Blockerad*, also in amber text), a blue dot for *Working* (*Arbetar*) and a ring for *Idle* (*Ledig*), then the agent's text on one line, cut with "…"; the tooltip (and the keyboard-focusable line's accessible name) has the whole text and when it was reported.
- **Question badge.** An open question puts an accent **?** badge after the tab's name, and on its project's row for a subtab's question (`?2` for two or more). Its tooltip is the question (or how many wait), its accessible name says whose questions it opens. A click, Enter or Space opens the questions below it: who asks and when, the text, the options as buttons and, when `free` allows it, a text field with *Send* (*Skicka*; Enter sends). The first answer control gets keyboard focus; Escape closes. The answer is written through the channel's answer API once: the controls are disabled while and after it is written, the badge disappears, and the status line says *Answer sent to Atlas: …*. If another window answered first, the panel says so instead.
- **Stale questions.** A question whose tab is closed or whose CLI has exited, or whose `expires_at` has passed, stays visible as stale: the badge turns grey, the panel explains why in amber and shows no working answer controls, only *Remove* (*Ta bort*), which hides it until the tab restarts. A restarted tab (new track) starts without the old questions.
- **Notifications.** With *Notifications* on, a new question (*Atlas has a question*, with the question as text) and a new *Done* or *Blocked* status (*Atlas is done* / *Atlas is blocked*) show one system notification each; events from before BoosterAI started do not notify. Clicking a question's notification (or a done/blocked one while the tab has an open question) shows the main window with that tab's questions open: the toast launches `boosterai:question`, whose process asks the running BoosterAI to open them, and on Linux notify-send reports the click back directly.

### CPU activity

Hooks and output timing miss an agent that waits for a silent process: a build, a test run or a background command prints nothing and starts no turn, so the tab used to read *Idle* (#215). BoosterAI therefore also measures, at every 2-second status poll, how much CPU each running tab's processes use, and shows *Working* (*Arbetar*) instead of *Idle* or *Activity unknown* while they work. The tooltip names the busiest process by its program name only (the kernel's `comm`, at most 15 characters, never its arguments) and its share of one core: *A process in the tab is using the CPU: dotnet (85% of one core)…*. *Running* from claude's hooks or recent output, *Watching* and the other states are left as they are. *Working* counts as working everywhere: auto-clear does not type `/clear` (and its idle time starts again when the work ends), a changed tab's restart asks first and offers **Restart when idle**, a row waiting for idle waits for the work too, and an orchestra reload is not sent.

How it is measured: the tab log's `start` line holds the PID and start time of the tab's shell (`$$` in `tab-lib.sh`). Each poll reads `/proc` once for all tabs: `/proc/uptime` as the scan's clock and every `/proc/<pid>/stat` (parent PID, program name, `utime + stime`, start time); on Windows through `\\wsl.localhost\<distro>\proc`, the same path the *Lost* check uses, with eight reads at a time (about 0.1–0.15 s for 130 processes), and no process is started for it. A tab's share is the CPU time its shell and all descendants (by parent PID) used since the previous scan, divided by the time between the two scans: a process seen before counts its growth, one started since then all its time, and a reused PID (another start time) is not mistaken for the old process. The scan only runs while at least one tab is *Running*, and only those tabs are measured.

- **Threshold: more than 10% of one core, in two readings in a row** (about 4 seconds); *Idle* returns after two readings at or below it, so one spike does not flip the status and one quiet moment in a build does not end it. Measured idle tabs in WSL stayed at 0–6.5% per reading (an idle codex up to about 6.5%, once near 11% for a single reading; idle claude and agy and the tab's own helper loops `bs_trim`/`bs_hup_watch` 0–2%), while `dotnet build`/`dotnet test` used 30–300% and `yes` about 90–100%. The agent CLI's own CPU counts too: a CLI streaming a reply is working; the threshold keeps an idle one *Idle*.
- **Only a process's own CPU time is counted**, not the children time (`cutime`/`cstime`) a parent collects when a child exits. That would count the tab's own once-a-second helper commands (`stty`, `sleep`) as 1–3.5% per tab and count again what earlier scans already saw. In return a process that starts and ends between two scans (under 2 seconds) is not seen; long builds and test runs are.
- **A quiet child stays *Idle*.** A tab whose agent waits for `sleep 300` or another process that does not use the CPU shows *Idle*, not a separate waiting state: every tab always has live children (the `script` recorder, `bs_pty`, the helper loops, MCP servers, codex's helper process), so "a child is alive" says nothing about whether work is going on.
- **How hard it works (#286).** The status dot of a working tab (*Running* or *Working*) shows its load in three levels from the same readings, smoothed so the dot does not change at every poll: each reading moves the smoothed share 40 % of the way towards it (starting from zero, so one spike after a start does not reach the top), and a level is entered at its upper threshold and left only below a lower one. **Low** (under 40 % of one core, left again below 25 %; an agent's turn waiting on its model): a calm, faint halo pulse every 2.6 s, up to 1.3 × the dot at 35 % opacity. **Medium** (from 40 %, left below 25 %; about one busy core, a single-threaded test run): every 1.6 s, 1.5 ×, 55 %. **High** (from 150 %, left below 110 %; a parallel build or test run): every 0.8 s, 1.75 ×, 85 %. With Windows animations off the halo stays still and shows the level by its size and strength (12, 14 or 16 px at 25, 40 or 60 % opacity). A tab working by its agent's turn without a CPU reading (the first poll, a failed scan) uses Medium. The status popup adds *Load: high (280% of one core)*; the dot's accessible name is unchanged. `--screenshot --fake-dots` shows the three levels, a turn without a reading, waiting, watching, starting, failed and closed rows (with animations off as a still screenshot).
- Not measured: a tab whose CLI has exited (its shell shows *Idle* even while you run something in it by hand), a tab whose shell is gone, and processes the work handed to something outside the tab (a daemon started with `setsid`/`nohup` that moves to init, a Docker container, Windows programs started from WSL).

### Show the tab in the terminal

A row whose tab has a terminal tab (Starting, Running, or a CLI that exited while the shell lives) switches Windows Terminal to that tab when you click a free part of the row: its name, the empty space around it or its background (#253; before that a separate terminal icon did it, #213). Such a row shows a hand cursor. The row's controls keep their own clicks and never switch: the tick, the folder icon, a subtab's name box and ×, the question badge, the status dot (its popup), Start, ↻, *Continue*, the Agent, Model and orchestra lists with their usage meters, the agent's status line, the drag grip and **⋯**. A press that moves more than a few pixels before release is no click, and dragging stays on the grip. Without a mouse, focus the row (its grip) and press Enter, or choose **Show in terminal** (*Visa i terminalen*) in the row menu; the grip's accessible help text says *Enter shows <tab> in the terminal* while this works. Closed and never-started rows do nothing on a click, their menu item is inactive and Enter keeps its old meaning. The click brings the window forward; otherwise only arranging the tab order does, briefly (see [Terminal tab order](#terminal-tab-order)).

On Windows it runs `wt.exe -w BoosterAI-<session> focus-tab -t <index>`. All tabs of a session open in that named window; the index is the tab's position in the window as BoosterAI last arranged or saw it ([Terminal tab order](#terminal-tab-order)), among the tabs that still have a terminal tab, with tabs it has no position for counted by start order (`tabN`); `--dry-run` prints `show tab <name>: ...` for each tab as if all were live and in row order. Limits: Windows Terminal's CLI addresses tabs only by index, so a tab the user dragged or opened by hand since the last arrange makes the index point at a neighbour until the next arrange sees it; a tab closed behind BoosterAI's back is noticed only at the next status poll. Linux terminals cannot select one tab from outside, so there a row click does nothing and the menu item is hidden.

### Terminal tab order

On Windows, BoosterAI keeps its tabs in the session's terminal window in the order of their rows (#254). Windows Terminal opens every `new-tab` at the end of the window and its command line can neither open a tab at a position nor move a tab, but `focus-tab -t <i> ; move-pane -t <beyond the last tab>` moves tab *i*'s pane into a new tab at the end, with its running process, title and colour (Windows Terminal 1.11 or later). So:

- **A tab opened into the open window** (Start, ▷, a restart or *Continue* of a closed tab) is appended by Windows Terminal; about 1.5 s later BoosterAI moves the tabs whose rows come after it to the end, in row order, and shows the new tab. A tab whose row is last needs no move, and a new window gets its tabs in row order from the start.
- **Reordering rows** (dragging, Alt+Up/Down, *Move up*/*Move down*) moves the open tabs to match, 0.8 s after the last change so several steps make one command. Windows Terminal brings its window forward for every `wt -w` command, which cannot be avoided; BoosterAI then takes the focus back (when it had it) and shows the tab that was selected before.
- Only the tabs that must move are moved: the longest start of the row order that is already in order stays. Closed tabs leave no gap.

To know the window's tabs BoosterAI reads their titles left to right with UI Automation (a hidden `powershell.exe`, read only, about half a second), in the window it opened and still tracks for [placement](#terminal-window-placement); BoosterAI's tabs are titled with their names (a renamed tab matches by the name it was started with or its new one, #281; a title a CLI set briefly is not recognised until the next status poll restores the name). So tabs the user dragged by hand and tabs the user opened in that window are seen. Those other tabs are never moved: BoosterAI's tabs keep their order among them, and a tab BoosterAI moves to the end lands after them. Equal titles are matched in BoosterAI's last known order. Without a snapshot (a window from before placement tracking, or the read failed) BoosterAI uses the order it last arranged or saw, saved per session in `<session>/window-order`; tabs the user opened or dragged by hand are then unknown and shift its indices. `--dry-run` prints two example commands (`terminal order, ...`).

Limits: when Windows Terminal is set to open new tabs next to the current one (`"newTabPosition": "afterCurrentTab"` in its `settings.json`), neither new tabs nor moved ones land at the end, so BoosterAI leaves the order alone (as before #254). A tab the user split into panes moves only its active pane. Linux terminals cannot place or move a tab from outside (GNOME Terminal, Xfce, Ptyxis and Konsole have no such command; kitty and WezTerm open each BoosterAI tab in its own window), and a reopened tab opens in a new window there, so on Linux the order is not arranged.

### Keeping project tab titles

While BoosterAI runs, its two-second status poll also restores each tracked tab's configured name, including subtabs and tabs recovered after reinstalling the app.
This corrects title changes during a long CLI run (a CLI may set its own title) and after
Windows Terminal reloads settings.
It always sends the row's current name, so a rename reaches an open tab within about two seconds; the poll also
rewrites the tab's `tabN.title` once per new name, which the shell's `bs_title` and idle prompt read (#281).
The refresh writes only an OSC title to the live shell's output PTY, after checking
its PID and start time twice. It never types into the CLI, switches tabs or moves
focus. Missing processes, non-PTY output and inaccessible terminals are skipped.
There are no persistent watcher processes; the short batched command is bounded
and reaped. On quitting BoosterAI the periodic correction stops; startup resumes it.

### BoosterAI window size

The main window remembers its normal client size (device-independent pixels) and
maximized state in `main-window.json` next to `config.json`. Resize/state changes
are saved after 250 ms and flushed when minimizing or closing, so an installer
that stops the process does not depend on a graceful exit. Minimized and tray-hidden
windows never replace the last normal size. Background startup stays minimized
without activation; showing it restores the remembered normal/maximized state.
Normal startup restores immediately. Sizes are constrained to the primary screen's
working area and the existing minimum window size. Missing, damaged or invalid
state falls back to 1100 × 560. Window position is not saved. Preview/screenshot
windows do not load or save this state; a custom config keeps its own adjacent file.

Background startup hides the main window only on its first opening. Later tray
or menu activation keeps it visible; minimizing it again still returns it to the tray.

## Auto-compaction budgets

Start with **Settings → Memory and context → Context**, section *Summarize (auto-compact)*. The page illustrates a growing conversation → agent summary → room for more work, with a visible reminder that summaries can lose details. A second static diagram explains known model capacity minus a work reserve → suggested compaction threshold, with code/orchestra examples and a labeled legend. These are scalable theme-aware illustrations, not live conversation meters or promises of exact summary size, cost, speed or quality.

The main Context choice is **Off**, **Clear when idle** or **Summarize**. Off leaves CLI defaults in place; Clear when idle enables the idle timer and removes BoosterAI compaction overrides; Summarize disables idle clearing and offers Auto or Manual budgets. Saved model budgets remain available in every mode. A legacy configuration with both clearing and summarizing enabled is explicitly shown as a retained combination with no main choice selected; opening or saving the page does not change it. Selecting one of the three choices explicitly replaces that combination. The explanation remains visible in every mode so you can understand Auto before selecting it. The current choice and its effect remain separate from the illustrations; opening the page changes no setting. Calculation details, model support and metadata status are expandable, while the agent-specific tuning shortcut remains available.

| Global mode | Behavior |
| --- | --- |
| **Off – CLI defaults** | BoosterAI sends no compaction override. The CLI can still compact automatically according to its own settings. This is the default for new configurations. |
| **Auto – recommended budget** | Uses known context metadata for the exact model and the explained task reserve below. Unknown/default/local models without verified capacity retain CLI defaults. Saved manual values are neither consumed nor modified. |
| **Manual – custom agent settings** | Uses the saved exact agent/model preferences. Models without an effective saved choice retain CLI defaults. |

The global choice is saved as `AutoCompactMode` (`off`, `auto`, `manual`) and participates in multi-instance config merging. An older config with effective saved compaction overrides migrates to Manual so its behavior is preserved; otherwise it migrates to Off. An explicit existing global choice wins, and an unrecognized choice falls back to Off. Auto is never enabled by migration.

Auto selects **Long orchestra run** for a tab that actually launches the orchestra, reserving 40% (at least 64,000 tokens), or **Code changes** for other tabs, reserving 25% (at least 32,000). It rounds the remaining budget down to thousands and obeys the CLI-specific bounds. Current known Claude model IDs use the documented native-window assumption; gateways, custom providers or restricted context modes may need verified capacity in Manual. Codex uses its asynchronously loaded context metadata. Before that metadata arrives, or after a failed/missing read, it uses CLI defaults. A late or superseded response cannot replace a newer result or a different WSL distro's metadata. Other agents without an automatic capacity source, including Aider and local Interpreter models, keep their CLI defaults in Auto; use Manual with verified capacity to tune them.

For manual tuning, open **AI agents → select an agent → Context**, choose an exact model ID, task profile and **CLI default**, **Recommended heuristic** or **Custom token value**, then **Save for model**. A visual budget bar compares the chosen token value to verified context capacity; exact values remain editable without slider rounding. Advanced capacity and calculation details are collapsible. All advanced fields, Save and **Restore defaults** are available only while the global mode is Manual. Switching global modes or agent pages preserves the same editor and its unsaved draft. Preferences are stored in `AutoCompactSettings`, keyed by agent/model/profile; the last saved profile is active for that pair. Restore defaults removes **all** compaction entries for the selected agent, including hidden models and inactive profiles, and resets that editor's unsaved draft. It does not change permission aliases, other agents, or external CLI configuration. **Unsaved edits (#188):** the model, profile, mode and token fields only save with **Save for model**, because they depend on each other and a half-chosen combination must never be written; so **Done** or closing Settings with a changed, unsaved draft asks *Spara / Släng / Avbryt* (*Save / Discard / Cancel*, Cancel is the default) instead of dropping it. Save writes the valid drafts, Discard leaves the saved settings untouched, Cancel keeps Settings open; nothing is asked when no draft differs from what is saved. The same question covers a WSL memory cap moved on the slider but not saved with **Save to .wslconfig**; `.wslconfig` is only written on Save. The alias list and **Return memory to Windows** already confirm each change and are unaffected.

The effective choice applies to new or explicitly restarted sessions. No running turn is interrupted automatically. A changed effective budget, including newly available metadata, updates the existing restart status; it does not trigger a restart. Exited restart/continue uses the current global policy for the original launched agent/model/orchestra choice. Standard/default-model tabs receive no guessed budget.

| --- | --- | --- |

Bare `total` uses Codex’s documented non-TOML string fallback, avoiding nested quotes across Windows Terminal. This does not change the model context window or the separate post-turn compaction setting. [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [per-run overrides](https://learn.chatgpt.com/docs/config-file/config-advanced). |

The launch also checks the generation, leaving basic legacy starts at their defaults. The legacy Python CLI's `context_window` is not an equivalent setting. The recommendation is a transparent heuristic, not an optimality or cost claim. From the verified context capacity it reserves 10% (at least 16,000 tokens) for short questions, 25% (at least 32,000) for code changes, or 40% (at least 64,000) for a long orchestra run. This reserve allows for the next turn, tool results and compaction overhead. Aider additionally reserves half of total context for code, map and instructions; large projects may need more. The remaining budget is rounded down to thousands and, for Claude, capped at its supported 1M maximum. If there is no room for a valid budget, there is no recommendation. A lower threshold leaves more room but spends more turns summarizing and may discard useful detail.

For the catalog's exact current Claude Opus/Sonnet/Haiku/Fable IDs, the UI starts with the officially documented native 1M window. The UI labels that assumption: check/override it for gateways, `CLAUDE_CODE_DISABLE_1M_CONTEXT` or other context restrictions. Codex capacity comes from a bounded, read-only projection of `models_cache.json` (in the tab's account's `CODEX_HOME`, see [Accounts per agent](#accounts-per-agent)) in the same login shell/WSL distro as the tabs: slug, context window and effective-context percentage only. No cache is copied or published. Banners are separated from metadata, absent/malformed/stale or custom-provider metadata can be replaced with a verified manual capacity, and missing capacity yields no recommendation. Local models, provider aliases and Interpreter model IDs require a capacity verified for the actual provider/runtime configuration. Global Off and a Manual per-model CLI-default choice emit no override, preserving external defaults. Custom mode permits an explicit positive threshold without guessing capacity; BoosterAI bounds numeric input to 10M (Claude's documented bound is narrower).

Permission aliases remain independent and keep their existing precedence; arbitrary custom wrappers may change how flags are interpreted. Orchestra selects the startup prompt and, in Auto, the long-run budget profile. Manual profiles affect only the budgeting heuristic. Auto-clear is separate: it empties an idle Claude conversation instead of summarizing it, so enabling it can discard history before the compaction budget is reached. A manual `/compact` remains the CLI's own command. Tests use temporary data and fake executables; verification makes no model calls and does not edit real CLI settings.
