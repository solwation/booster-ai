# #248 verification: the status channel's agent side

Verified in WSL Ubuntu (Linux) on the commit that adds this file, rebased onto `f0fdc0e` (#249).

- **Build and tests.** `dotnet build src/BoosterAI -c Release`: 0 warnings, 0 errors. `dotnet test tests/BoosterAI.Tests` (WSL): 1653 of 1654 passed. The one failure was `TabLogoTests.SplashIsCentredFadesOutAndRestoresTheScreen` (a timing test, unchanged here), which passed when run again on its own (48/48). The 30 tests in [TabChannelAgentTests](../../../tests/BoosterAI.Tests/TabChannelAgentTests.cs) ([list](tests-tabchannelagent.txt)) cover:
  - the command lines of every CLI with the setting on and off, including start, continuation, the install prompt and both in-place restarts. They contain no `;` and no `"`. With the setting off nothing of the channel appears. Run once and Save and close register nothing. Claude gets no `--strict-mcp-config`, and its new options come after the prompt;
  - the session files and the limits the script shares with the reader, including `expires_at`;
  - an **MCP handshake** against the real server (`python3 -I <session>/bin/boosterai-tab mcp`): `initialize`, `ping`, `tools/list` and `tools/call` for status and ask. The ask is answered through `TabSession.Answer`, and the server keeps answering a ping while the ask waits. The tests also cover the timeout result, cancellation, an unknown tool and an unknown method;
  - the `boosterai-tab` command;
  - a **real pseudo-terminal run** (`script -qefc`) of the generated tracked tab script with the channel on. A stand-in `claude` finds `boosterai-tab` on PATH, starts the server named by its `--mcp-config`, reports status and asks. The test answers through `TabSession.Answer` and checks that the stand-in gets *The user answered: …* back, along with the three events, the variables and the instruction argument.
- **`--dry-run`** with a neutral config ([config](dry-run-config.json): claude, codex, agy, and a claude Run once): [on](dry-run-on.txt). With the setting off, the whole output is byte-identical to the base revision `c2dff82` except for the one channel description line ([diff](dry-run-off-vs-c2dff82.diff)), so every tab script is unchanged.
- **Real Claude Code 2.1.332** (`claude -p --model haiku`, with the tab's flags): [claude-real-run.txt](claude-real-run.txt). The server connected next to the user's own MCP server, so nothing of the user's was dropped. The agent called `boosterai_status` with `done` from the instruction alone. Asked about something only the user knows, it called `boosterai_ask` with options, got the answer that a stand-in for BoosterAI wrote in the answer format, then reported `done`. No permission prompt appeared.
- **Real Codex 0.172.0**: `codex <the tab's -c overrides> debug prompt-input` (no model call) shows the instruction as a developer message and the started server's tools under `mcp__boosterai` ([codex-prompt-input.txt](codex-prompt-input.txt)). `codex mcp get boosterai` with the same overrides shows the server, the `env_vars`, `tool_timeout_sec: 3660` and `default_tools_approval_mode: approve`. An invalid mode value is rejected with the accepted list `auto, prompt, writes, approve`.
- **Windows Terminal: not run.** No portable Windows Terminal is present on this machine: `WindowsTerminal.exe` was searched for under `%TEMP%`, `%LOCALAPPDATA%` and the non-system folders of `C:\`, and the earlier `.portable` roots are gone. The packaged one cannot be used, see #174. Project policy also leaves the real-tab check to the conductor at integration. [CommandCheck](CommandCheck/Program.cs) is ready for it and builds. It is adapted from #242: private desktop, no focus change, no `;` in the script. It opens the real tracked script with the channel on and a session under `%TEMP%` (so `/mnt/c` and its file modes are exercised). A fake `claude` checks `boosterai-tab` on PATH and the variables, does an MCP `initialize` with the server from its `--mcp-config`, and reports `done`. BoosterAI then reads that status from the events file. Run it with Windows .NET 10: `dotnet build docs/verification/248/CommandCheck -c Release`, then `dotnet <dll> <report.json> <portable WindowsTerminal.exe>`.
- **Not verified:** whether `default_tools_approval_mode=approve` avoids a prompt in an interactive Codex TUI; no interactive codex session was run. A Linux desktop terminal was not tested.
